# SPI-1172: usage limits and refused credentials, classified per API

Stage `p1172`, 2026-11-16. Evidence is in [`spi-1172/`](spi-1172/), for the code at `b7d7ba4` (deployed from it; the
later commits are docs). A failed answer from a Model endpoint is now classified by the endpoint's **API and auth**, from
what each vendor documents as machine-readable: the status, the error's type and code, and the reset headers and fields.
It is never classified from a message's prose. This applies to Durable turns, compaction, text generation and relayed
CLI requests. A usage limit pauses the thread with its reset and never falls back to another endpoint. Overload and 5xx
are retried, and "overloaded" is not a usage limit. Error text is redacted (keys, bearer tokens, JWT-shaped values)
before it reaches t3 or a log.

An error inside a stream that began with 200 is read from pi-ai's text. That text is Anthropic's JSON error, or a
Responses `response.failed` event's `<code>: <message>`. The status comes from the type or code.

**Recorded answers.** `packages/models/test/fixtures/vendors.json` holds 28 answers and 2 streamed errors. Each is in
the shape its source documents, with the source URL and the read date (2026-11-16). No vendor was called. The file is
made by [`spi-1172/gen-vendor-fixtures.mjs`](spi-1172/gen-vendor-fixtures.mjs). The sources:

- Anthropic: [errors](https://platform.claude.com/docs/en/api/errors), [rate limits](https://platform.claude.com/docs/en/api/rate-limits).
- OpenAI: [error codes](https://platform.openai.com/docs/guides/error-codes), [rate limits](https://platform.openai.com/docs/guides/rate-limits).
- ChatGPT's backend: [codex-rs `api_bridge.rs` at 662a634e](https://github.com/openai/codex/blob/662a634e88fcc809d77da393d75572c3d814cb27/codex-rs/codex-api/src/api_bridge.rs).
- Plan usage: [errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).
- Anthropic's unified limit headers are not in Anthropic's docs. Their names and the reset's unit come from Claude Code
  2.1.325's client (`strings` of the installed binary) and the Claude Agent SDK 0.3.321's `SDKRateLimitInfo`.

## Escalations

### 👀 Worth a glance (assumed, provisional)

- **P1: Relayed CLI requests are classified for the log, and the CLI pauses itself.** The relay passes an error back in
  the vendor's shape, redacted. Codex reads `usage_limit_reached`/`resets_at`, Claude Code reads the unified headers, and
  t3's stock adapters turn that into t3's usage limit. The relay logs `failure: {class, code, resetAt}` but does not
  mark the thread itself, because the CLI owns its turn. A CLI that does not read a vendor's limit shows it as its own
  error. ➡️ Keep; reconsider if a CLI's thread ever fails on a limit without pausing.
- **P2: A 429 with a reset stops the run and pauses the thread, even when the reset is seconds away.** It is held to at
  least 30 s by t3's resume rule. One request, an exact reset and auto-resume, as step-2a2 §3 has it. Without a reset,
  pi-durable retries, and a final failure is a usage limit with no auto-resume. ➡️ Keep.
- **P3: The Model proxy keeps its Commissary-prose classifier** (`proxyFailure.ts`) for the proxy's `anthropic` provider
  until the hard cut. The Commissary *endpoint* uses the per-API table, where its cooldowns are 429s with `retry-after`.
  ➡️ SPI-1176 deletes `proxyFailure.ts` with the proxy.
- **P4: No reset is read from prose.** Anthropic's spend cap ("You will regain access on …") and plan usage's limit (no
  reset, by OpenAI's instruction) pause without auto-resume. ➡️ Keep: the ticket says not to parse prose.
- **P5: Anthropic's unified headers are undocumented.** They are read as Claude Code's client reads them. A rename is
  silent (U79). ➡️ Keep; the rows fall back to the 429's `retry-after`.

### 🌳 Decisions

- **D1** The failure codes avoid pi-ai's retry patterns: `throttled`, not `rate_limited`, which `rate.?limit` would
  retry. This is tested against pi-ai's own `isRetryableAssistantError`.
- **D2** The record is new: `ProxyRecord.endpointFailure`, with the Session's text, so the differ needs no endpoint
  list. The proxy's `failure` and an endpoint's clear each other, so the last failed answer is the turn's.
- **D3** An endpoint's answer is classified only when the message's provider is the endpoint and the recorded URL is
  under its base URL. Google's and Mistral's clients take no fetch, so for them the text alone is read, as a stream
  error's is.
- **D4** Text generation's wording follows the table: 429 is "is rate-limited (HTTP 429)", 503/529 is "is overloaded",
  and a usage limit says when it resets.
- **D5** The relay reads at most 16 KiB of an error body and drops `content-length` and `content-encoding` from the
  redacted answer. Success bodies stream unread.
- **D6** Parallel SPI-1165: the refused row is per auth over `SIGN_INS`, so a Claude sign-in kind gets
  `sign_in_refused` with its own title and hint. The unified-limit row applies to any Anthropic Messages endpoint,
  whatever its auth.

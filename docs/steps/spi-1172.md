# SPI-1172: usage limits and refused credentials, classified per API

Stage `p1172`, 2026-11-16. Evidence is in [`spi-1172/`](spi-1172/). Review round 2's evidence is for the code at
`97d322a`, deployed from it. (Round 1's was at `eeff163`; its files were replaced by round 2's run.) A failed answer from a Model endpoint is now classified by the endpoint's **API and auth**, from
what each vendor documents as machine-readable: the status, the error's type and code, and the reset headers and fields.
It is never classified from a message's prose. This applies to Durable turns, compaction, text generation and relayed
CLI requests. A usage limit pauses the thread with its reset and never falls back to another endpoint. Overload and 5xx
are retried, and "overloaded" is not a usage limit. Error text is redacted (keys, bearer tokens, JWT-shaped values)
before it reaches t3 or a log.

A retried code's text is worded so that one of pi-ai's retry patterns matches it (`overloaded`, `server error`, `rate
limit`, `service unavailable`). So a bare 529, 521 or 507 is retried, whatever the vendor's body said.

An error inside a stream that began with 200 is read from pi-ai's text. That text is Anthropic's JSON error, or a
Responses `response.failed` event's `<code>: <message>`. The status comes from the type or code.

**The answers are doc-shaped, not recorded from vendors.** `packages/models/test/fixtures/vendors.json` holds 33 answers
and 2 streamed errors. Each is written in the shape its source documents, with the source URL and the read date
(2026-11-16). No vendor was called with real credentials to record one, as the ticket's brief asks. The file is made by
[`spi-1172/gen-vendor-fixtures.mjs`](spi-1172/gen-vendor-fixtures.mjs). `resets_in_seconds` was dropped: no source names
it. The sources:

- Anthropic: [errors](https://platform.claude.com/docs/en/api/errors), [rate limits](https://platform.claude.com/docs/en/api/rate-limits).
- OpenAI: [error codes](https://platform.openai.com/docs/guides/error-codes), [rate limits](https://platform.openai.com/docs/guides/rate-limits).
- ChatGPT's backend: [codex-rs `api_bridge.rs` at 662a634e](https://github.com/openai/codex/blob/662a634e88fcc809d77da393d75572c3d814cb27/codex-rs/codex-api/src/api_bridge.rs).
- Plan usage: [errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).
- Anthropic's unified limit headers are not in Anthropic's docs. Their names and the reset's unit come from Claude Code
  2.1.325's client (`strings` of the installed binary) and the Claude Agent SDK 0.3.321's `SDKRateLimitInfo`.

## Review round 1

Rebased onto `fad9b7a` (SPI-1170). The fragility entry is now **U79** (SPI-1170 took U78): the entry, the check table
and U14's pointer.

1. **Relayed CLI failures are classified per API** (blocking).
   - **How it is wired.** The relay classifies each answer by the endpoint's API and auth, with the full headers and
     body. It reports the result to the Workspace DO as the process's last answer: `modelRelayOutcome`, the failure, or
     null for a success or an unknown error. A turn's start clears it (`processTurn`). The Environment's CLI wrapper
     handles a failed `turn.terminal` and the `error` turn items for every CLI. It asks the process for that record
     (`processModelFailure`), and `cliRelayFailure` puts it in t3's failure: class, the text naming the endpoint, code,
     and a reset held to 30 s after now.
   - **Why the relay, not the CLI's text.** The CLIs drop the headers, so a reset would be lost. Their error texts
     differ, and t3's adapters for Codex and pi never call our flavor.
   - **With no record on an endpoint's model**, the proxy classifier's result (`proxy_*` codes, or the
     `COMMISSARY_CONTAINER_API_KEY` text) gives way to a plain error naming the endpoint. On the proxy's model, the old
     classifier stands.
   - **No other path:** Codex and pi never reached `classifyProxyFailure` (t3's own adapters classify their failures).
     They now get the relay's classification through the same wrapper.
   - **Tests** (`cliRelayFailure.test.ts`):
     - Claude Code and OpenCode on t3's real ACP adapter with a scripted agent failing "API Error: 401 …": a refused
       key, a usage limit with its reset, and no record on an endpoint versus on the proxy.
     - Codex and pi through a stand-in of their adapters' failures.
     - The Workspace DO's `RelayFailures`, and the relay's reports (`modelRelayRoute.test.ts`).
     - Stage: pi and Codex above.
2. **The last answer wins** (blocking). Every failed answer replaces the turn's record. An unknown one clears it, for
   the proxy's record as for an endpoint's. Tests: a retried 529 then a "prompt is too long" 400 leaves no overload; the
   same on the proxy path.
3. **Retries.** A retried code's text matches one of pi-ai's retry patterns, so bare 529, 521 and 507 answers are each
   retried, four requests in all. 501 is `unsupported_request`, not retried (Not Implemented does not change on retry).
4. **JSON-safe redaction.**
   - A key's JSON value is replaced only inside its string, so `"api_key": null` stays null. No value runs past a quote
     or a backslash, so an escaped body keeps its escapes.
   - The relay redacts only the credential header's value (and a bearer's token), never another header's.
   - A property test redacts 500 random JSON documents planted with secrets: each still parses and holds none.
5. **The relay never cuts a body.** An error body is redacted whole, up to 1 MiB. A larger one is replaced by a short
   error in the API's own shape. Tested with a 20 KiB body and an over-1 MiB body.
6. **Redaction gaps.**

   - New shapes: `xai-…`, `gsk_…`, `Basic …`.

     rest of the stream passes through unchanged, line by line. In the Session, such an error reaches the hook as
     pi-ai's text, already redacted and classified.
7. **Classifier gaps.**

8. **A short 429 is retried, not paused.** A reset at most 60 s away (`SHORT_RESET_MS`, pi-ai's own retry-delay cap; 14 s since round 2) is

### 🌳 Decisions

- **D1** A stopped failure's text in pi-durable names its class, not its code ("t3flare model endpoint: usage_limit, not
  retried"), so no retry pattern of pi-ai's matches it whatever the code (`rate_limited` would match `rate.?limit`). A
  retried code's text matches one of the patterns. Both are tested against pi-ai's own `isRetryableAssistantError`.

# SPI-1174: Limit meters for subscription endpoints

t3's limit meters now show each subscription endpoint's windows as one limit source per endpoint: ChatGPT's primary
and secondary windows and Claude's five-hour and weekly ones, each with its used share and its reset, read from the
rate-limit headers of the answers the Durable agent (and text generation) and the model relay (every CLI) see. A meter
not read for 30 minutes says when it was last read. Evidence is in [`spi-1174/`](spi-1174/). Fragility:
[U84](../upstream-fragility.md#u84-limit-meters-for-subscription-endpoints-vendors-limit-headers-and-t3s-limit-source-contract-spi-1174)
(U58 points at it). Glossary: **Limit reading**.

**No live subscription run** (the owner's decision during SPI-1171): no ChatGPT or Claude subscription was signed in. The
acceptance's "plausible percentages and resets after real turns" on the real subscriptions is **unverified**; the stage
ran real turns (the Durable agent, Claude Code, Codex) against the probe Worker standing in for both vendors, answering
in each vendor's header shape.

pi-ai 1.5.0 reads none of these (its `openai-codex-responses.js` only classifies a 429), so nothing is lost to it: the
readers sit on the request's `fetch`, which sees the answer's headers before pi-ai does.

**ChatGPT plan usage sends no Codex headers today, as far as is known.** Our ChatGPT sign-in is OpenAI's plan usage on
`api.openai.com/v1` (SPI-1164), not the Codex backend. A third party reported on 2026-10-14
([openai/codex#54219](https://github.com/openai/codex/issues/54219)) that a token from that flow gets no
`x-codex-primary-*` headers and no rate-limit event on `/v1/responses`, and that `wham/usage` refuses it; the issue asks
OpenAI to add them. So the ChatGPT meter is built and tested on the Codex headers, but will appear only if OpenAI sends
them to plan usage (or on an endpoint whose answers carry them, such as the Codex backend through a gateway). Escalation
E1.

### Strict and defensive

- A value is read only in its documented form: digits and one decimal point (`/^\d{1,9}(?:\.\d{1,9})?$/`); no sign,
  exponent, unit or `%`. A whole number for minutes and resets.
- A used share is clamped to 100 % (an overspent window is spent, as Codex's and Claude Code's displays clamp). A
  negative or garbage share drops the window.
- A reset must be after the answer and within 366 days of it (a reset in milliseconds, in the past or absurd is dropped,
  the window kept). A length must be 1 minute to 31 days.
- Codex's all-zero window (no use, no length, no reset) is dropped, as Codex drops it.
- A Claude claim the answer refused with no utilization is spent (100 %): its own `-status: rejected`, or the overall
  `rejected` naming it as the representative claim, with the overall reset. So a usage-limit 429 sets its meter.
- Nothing throws into an answer: the reader catches everything, and a failed send loses that reading only.
- The Environment accepts a reading again (`acceptedLimitReading`): a known endpoint id, a time, known window ids with a
  share from 0 to 100; unknown fields (a token, an account) are not kept.

## Where readings are made and kept

| Seam | What | Where |
| -- | -- | -- |
| **Durable** | Each endpoint request's answer (a failed one too), on the endpoint's fetch, beside SPI-1173's `answering`: API-key, no-auth and sign-in endpoints alike, on the APIs whose pi-ai client takes a `fetch` (Anthropic Messages, OpenAI Responses and Completions; Google and Mistral send no window headers) | `apps/agents/src/session/models.ts` (`limitWatch`, `endpointFetch`; `EndpointAccess.limits`), `session/endpoints.ts` (a required `limits` option), `SessionDO.ts` |
| **Text generation** | Its one answer | `endpointText.ts`, `endpointTextGeneration.ts` |
| **Relay** | Each CLI request's upstream answer, its headers read before the CLI has the answer, a refused one included | `apps/agents/src/workspace/modelRelay.ts` (`noteLimits`; required in `workspaceRelayDeps`), `workspaceProxy.ts` |

All three send through `limitsSender` (`apps/agents/src/environment.ts`), built on the same helper as SPI-1173's
`usageSender`: the Environment DO's `recordLimits` RPC (never boots t3) in `ctx.waitUntil`. A failed send is logged by its
endpoint only.

**Where the readings live.** The Environment DO's SQLite, table `t3flare_limit_windows` (`apps/environment/src/usage/
limits.ts`): one row per endpoint and window, holding the share, the reset, the length and `at`. So they survive an
eviction (tested on a new store over the same database; the stage's stale check ran after the Environment had been idle
for half an hour). Bounded by the endpoints: at most four windows each, and a removed endpoint's rows go at the next
write. **No token, account or organization** is in a row: `anthropic-organization-id` is not read, and the readings
carry no account (t3 names the meter by the endpoint's id and shows the endpoint's label as "Via").

**Concurrency: the latest answer wins, per window.** `at` is when the answer's headers arrived where they were read. The
upsert replaces a window only when the new reading's `at` is later (`ON CONFLICT … WHERE excluded.at >
t3flare_limit_windows.at`), so an older answer's reading that arrives later never overwrites a newer one, however many
Sessions and CLI processes answer at once. Each window is kept apart, since an answer may report only some (SPI-1161's
Claude answers had the `7d` window only). A reading timed more than an hour ahead of the Environment's clock is dropped.

## t3's meters (Layer, no Shadow or Patch)

`usage/limitSources.ts`, the Layer over t3's `UsageLimitSources` that already added Commissary's accounts (U58), now
composes any number of our sources (`withSources`): Commissary's, and `endpointMeterSources`, built from the kept
windows and the endpoints now (`limitSnapshots`):

- one source per endpoint with a kept window: id `t3flare-endpoint-<endpointId>`, kind `cliproxy` (t3's only kind), its
  label the endpoint's; one account per vendor family, named by the endpoint's id, driver `codex` (ChatGPT) or
  `claudeAgent` (Claude), so t3 pools them with its own Codex and Claude meters;
- each window with its share, its reset, its length, a label by its length ("5-hour", "Weekly") and t3's kind
  (`session`, `weekly`);
- **staleness**: a window not read for 30 minutes (`STALE_AFTER_MS`) gives its source t3's `error`, which t3 shows as a
  notice beside the meters, on the Usage page (`collectLimitNotices`) and in the composer's `/usage-limits` report
  (`collectProviderUsageLimits`): "Last read 3 hours ago (limits are read from this endpoint's answers)." When only some
  windows are stale it names them ("Weekly last read 2 days ago (…)"). The meter itself stays (t3 hides an account only
  for its own `unavailable`, which we never set);
- a window whose reset has passed shows reset (0 % used, no reset time) until an answer reads it again: the vendor's
  window has reset.

The source updates at once when a reading is kept (the store calls back synchronously inside `recordLimits`, and the
Layer republishes), and is looked at again every minute (`ENDPOINT_METERS_EVERY`) and on t3's refresh, publishing only
a changed list, so a meter goes stale and a reset passes without an answer. A reset-credit claim on one of our sources is
refused ("claim a reset with the vendor").

## Seams tested

- **The vendors' header shapes** (`apps/environment/test/limitMeters.test.ts`): each vendor's names and units pinned
  (Codex's percentage and epoch seconds; Claude's fraction and epoch seconds, a 7d-only answer, a refused claim by its
  status and by the representative claim); no window from Copilot's or an API key's `x-ratelimit-*` or
  `anthropic-ratelimit-requests-*`; garbage (`lots`, `-1`, `1e2`, `NaN`, `12.5%`, …), clamping, Codex's all-zero window,
  past, millisecond and absurd resets, bad lengths; a throwing headers object. What the Environment accepts.
- **The store** (Node's SQLite): the latest answer wins whatever order the sends arrive in, per window; an equal time
  changes nothing and tells no one; unknown endpoints and future readings dropped; a removed endpoint's rows pruned; a new
  store reads what an earlier one kept; no token, email or org in the table.
- **t3's view**: our sources decode with t3's own `UsageLimitSourceSnapshot` schema; t3's own `collectLimitAccounts`
  and `collectLimitPools` make a Codex pool and a Claude pool with the right remaining shares; `collectLimitNotices` and
  `collectProviderUsageLimits` carry the staleness notice; the 30-minute boundary on both sides; mixed staleness; a
  passed reset; labels by length. The Layer: a kept reading shows at once through `current`, a refresh after time passes
  shows the notice, a reset claim is refused.
- **The readers** (`apps/agents/test/limitReadings.test.ts`): pi-ai's real Anthropic and Responses clients through the
  Session's providers (an API-key endpoint and the Claude sign-in's provider), reading the windows under the endpoint and
  the answer's time, with no token or org; the stage fault's refused limit (through the recording fetch) as its claim
  spent; nothing from an answer with no window; a throwing reader leaves the answer whole; text generation; the relay
  reading a stream's headers and a 429's, passing headers and body unchanged, nothing from garbage, a throwing reader
  harmless; `limitsSender` and its failure log.
- **Mutants**, each applied, failing a test, then reverted: the upsert's `WHERE` (latest wins), Claude's `×100`, the
  Session's fetch left unwatched, the relay's `noteLimits` removed, the stale boundary `>=` to `>`, the store's
  subscription dropped.

## Escalations

### 🙋 Need you

❓ **E1: The ChatGPT meter will likely stay empty on our ChatGPT sign-in.** Plan usage (`api.openai.com/v1`) is reported
to send no `x-codex-*` headers (openai/codex#54219, a third party, 2026-10-14), and we hold no other read of plan usage
(`wham/usage` refuses its token, per the same report). The meter is built on Codex's own headers, so it lights up the day
OpenAI sends them, or on an endpoint whose answers carry them. Options: leave it (my recommendation); or add a manual
"usage on chatgpt.com" link source (t3's `externalUsage`) for the ChatGPT sign-in, which needs no header. ➡️ Leave it;
check on the first live ChatGPT turn (the Usage page shows a ChatGPT meter or not).

### 👀 Worth a glance (assumed, provisional)

- **P1: Staleness after 30 minutes**, shown as the source's notice (t3's `error`), beside the still-shown meter. t3 has
  no field for a reading's age, and its web client shows none; the notice is t3's own path for a source's message, so no
  Patch. ➡️ Keep; a Patch could show it on the bar itself if the owner wants.
- **P2: A window past its reset shows 0 % used** with no reset, until the next answer reads it. ➡️ Keep (the vendor's
  window has reset).
- **P3: Readings on any endpoint whose answers carry the headers**, not only sign-ins: an API-key gateway that passes a
  subscription's headers through (Commissary on a Claude account) gets a meter too. ➡️ Keep; the headers are
  subscription-only, so an API key's answers never make one.
- **P4: Copilot has no meter** (no documented header). ➡️ Keep; SPI-1226 may revisit with Copilot's account API.
- **P5: A sign-out and a sign-in to another account on the same endpoint** keeps the old account's windows until the
  next answer replaces them (or they go stale). No identity is kept to tell accounts apart. ➡️ Keep.
- **P6: Codex's other limit families** (`x-<limit>-primary-*`, model-specific limits) are not read. ➡️ Keep until one
  is seen on a subscription.

### 🌳 Decisions

- **D1** One reader per seam where SPI-1173 reads usage: the Session's per-endpoint fetch (beside `answering`), text
  generation's (the same providers), the relay's upstream answer; one sender helper shared with `usageSender`; a new RPC
  `recordLimits` beside `recordUsage`.
- **D2** Stored per window in the Environment DO's SQLite, the latest answer's by `at`; memory only for the t3 view.
- **D3** The source's account is named by the endpoint's id and the source by its label: no email, plan or workspace.

# SPI-1161: pi-ai's subscription sign-ins and a streaming model relay in Workers (spike)

Stage `p1161`, 2026-11-14 to 2026-11-15. pi-ai 1.5.0, Codex CLI 0.167.2, Claude Code 2.1.322. Evidence is in
[`spi-1161/`](spi-1161/), one file per question and case. It records shapes, header names, statuses, timings and
expiries, never a token, a refresh token, a code or a handle.

**Probe commits.** The probe routes were on `d4a883f`, then `4cd011c` (durable paste flows), `e2b8635` (a pasted
callback without its scheme) and `7927962` (plan read, off-Worker credential export). All four are reverted by
`3c48af9`, so nothing of them is in the final diff; read them with `git show <sha>`. The probe was a `SigninProbe`
Durable Object in the agents Worker (`apps/agents/src/probe1161.ts`). It had admin routes at `/_t3flare/probe1161/*`
behind Access and the admin token, and a public relay route at `/api/probe1161/relay/<vendor>/*` gated only by a
handle. Both refused unless `T3FLARE_FAULTS=1` and the `SIGNIN_PROBE` binding was set, neither of which prod has.

**The owner's accounts:** ChatGPT **Free** plan (the token's `chatgpt_plan_type` claim is `free`, see
[`q3-codex-plan.json`](spi-1161/q3-codex-plan.json)), Claude Pro/Max, and a GitHub account whose **Copilot
subscription has ended**. He signed in from a phone.

## Q1. Do pi-ai's sign-in flows run in workerd?

**They load.** Evidence: [`q1-environment.json`](spi-1161/q1-environment.json).
- In the agents Worker (`nodejs_compat`), `process.versions.node` is `22.23.4`.
- `node:http`'s `createServer` exists, and `listen(1455, "127.0.0.1")` answers "listening" with an address, but nothing can reach that server.
- `node:crypto`'s `randomBytes` and `node:zlib`'s `zstdCompressSync` exist, and so does `WebSocket`.
- `openai-chatgpt.js` imports `node:http` and `node:crypto` at its top level. It loaded without error.

**Bundling needs one call.** pi-ai's `auth/oauth/load.js` imports each flow through a variable specifier, which a
bundler cannot follow, and the Rolldown build leaves those imports unresolved. Calling `registerBunOAuthFlows()` from
`@earendil-works/pi-ai/bun-oauth` once at module load registers all nine flows statically, and the bundle then holds
them. `registerBundledOAuthFlowLoaders` would allow registering fewer flows, but pi-ai does not export it (only
`./bun-oauth` is exported). The cost is that the providers we don't use are bundled too.

**Browser methods:** both start, and fall back to a paste prompt
([`q1-codex-browser-start.json`](spi-1161/q1-codex-browser-start.json),
[`q1-anthropic-browser-start.json`](spi-1161/q1-anthropic-browser-start.json)). Because `listen` seems to succeed,
pi-ai believes a callback server is running, and Anthropic's browser method sends `localhost:53692` as its redirect.
Only the device-code and copy-code methods should be offered.

**Device codes work as shipped.**
- ChatGPT: a code from `auth.openai.com/api/accounts/deviceauth/usercode`. The owner enters it at
  `https://auth.openai.com/codex/device`. It lasts 15 min and is polled every 5 s. The exchange at
  `auth.openai.com/oauth/token`, with redirect `https://auth.openai.com/deviceauth/callback`, succeeded from the
  Worker. Completed 360 s after the start.
- Copilot: `github.com/login/device`, polled from the Worker until authorized (398 s). The next step,
  `api.github.com/copilot_internal/v2/token`, answered `403 subscription_ended`.

**pi-ai's `login()` cannot be relied on in a Durable Object.** It keeps the PKCE verifier, the state, and its wait for
the paste in memory.
- In all three rounds, the copy-code and paste-URL flows had dropped out of the object's memory before the owner's
  paste arrived: within 8 minutes in the third round. That happened even though an alarm every 15 s kept the object
  busy (151 alarms ran).
- Round 3's device flow survived only because it finished within 6 minutes.
- A redeploy also drops every running login.

**What the sign-in tickets must build** (the probe's `startDurable` and `pasteDurable` in `4cd011c` are a working
sketch):
- **Start.** Make the PKCE verifier (32 random bytes, base64url) and the challenge (S256). Keep `{verifier, state,
  startedAt}` in the Environment DO's storage under the flow's id, and return the authorize URL.
  - **Anthropic:** `https://claude.ai/oauth/authorize?code=true&client_id=<pi-ai's>&response_type=code&redirect_uri=https://platform.claude.com/oauth/code/callback&scope=org:create_api_key user:profile user:inference user:sessions:claude_code user:mcp_servers user:file_upload&code_challenge=…&code_challenge_method=S256&state=<verifier>`.
    pi-ai uses the verifier as the state; we kept that.
  - **ChatGPT device code:** keep `device_auth_id` and `user_code`, and poll
    `auth.openai.com/api/accounts/deviceauth/token` from the DO's alarm rather than in a loop. A 403 or 404 means
    pending. On success the poll returns `{authorization_code, code_verifier}`; exchange them at `/oauth/token` with
    pi-ai's client id and the device redirect.
  - **Copilot:** keep `device_code`, and poll `github.com/login/oauth/access_token` from the alarm.
- **Paste (Anthropic).** Split the pasted `code#state`, check the state, and POST JSON to
  `https://platform.claude.com/v1/oauth/token` with `{grant_type: "authorization_code", client_id, code, state,
  redirect_uri, code_verifier}`. It completed 182 s after the start
  ([`q1-anthropic-paste-durable.json`](spi-1161/q1-anthropic-paste-durable.json)).
  - The response has the fields `access_token`, `account`, `expires_in` (28800), `organization`, `refresh_token`,
    `refresh_token_expires_in`, `scope`, `token_type`, `token_uuid`.
  - The granted scope **lacks `org:create_api_key`**.
  - The access token starts `sk-ant-oat01-` and the refresh token `sk-ant-ort01-`.
- **Store.** Write the credential in pi-ai's `OAuthCredential` shape (`{type: "oauth", access, refresh, expires,
  …extras}`; ChatGPT adds `accountId`), so that pi-ai's `refresh` and `toAuth` (`provider.auth.oauth`) and
  `Models.getAuth` work on it unchanged. That part of pi-ai works in workerd and is worth keeping.
- **Accept the paste loosely.** Expect a code or a URL pasted from a phone, with or without its scheme
  ([`q2-openai-paste-durable-2.json`](spi-1161/q2-openai-paste-durable-2.json) records the forms that arrived).

## Q2. ChatGPT token sharing (`openai-chatgpt`) with a pasted 127.0.0.1 redirect

**No-go as tested**, and the cause is not settled. Evidence:
[`q2-openai-paste-durable-2.json`](spi-1161/q2-openai-paste-durable-2.json),
[`q2-openai-paste-durable-3.json`](spi-1161/q2-openai-paste-durable-3.json).

**What worked:**
- The authorize URL (`auth.openai.com/api/accounts/authorize`, `client_id=dynamic_agent_client`,
  `ext_agent_host_id=urn:uuid:<device id>`, `resource=https://api.openai.com/v1`, `scope=… resource.invoke
  chatgpt.tokens.use.direct`) let the owner approve from his phone.
- OpenAI then redirected to `http://127.0.0.1:1455/auth/callback`. The page failed to load, as expected. He copied the
  address bar, a 2109-character URL with `http://`, holding `client_id` (an issued `oaiapp_…`), `code`, `scope` and
  `state`. The state matched.
- So the redirect could be completed by a paste.

**What failed:** the exchange at `auth.openai.com/api/accounts/oauth/token` (form-encoded: `authorization_code`, the
issued client id, `code`, `code_verifier`, `redirect_uri`, `resource`), sent from the Worker, answered
`400 {"error":"invalid_grant"}` twice. The second time was a fresh flow, approved once and pasted at once (6.5 min
after its start). The first try was lost with pi-ai's in-memory flow, and the second (`-2`) reused an authorize URL
the owner had already approved once.

**Possible causes, which these attempts cannot tell apart:**
- **(a) Plan entitlement.** The owner is on ChatGPT Free, and token sharing (`chatgpt.tokens.use.direct`) may require a
  paid plan. OpenAI's consent page still issued a code, and the error body says nothing more than `invalid_grant`.
- **(b) A refusal of the Worker's request.** The same host's device-flow exchange (`/oauth/token`) worked from the
  Worker, and the endpoint answered with OpenAI's own JSON, not a challenge, so this looks less likely. But we never
  sent the exchange from any other egress.
- Code expiry or reuse explains the second attempt at most, not the third.

**No mutating check is left to us:** each code is single-use. To settle it, repeat the flow with a paid account, and
send the exchange from the laptop as well.

**Recommendation:** leave ChatGPT token sharing out of the first sign-in tickets. Offer ChatGPT through the Codex
backend (`openai-codex`), whose device code works.

## Q3. A Durable turn with tools through pi-ai's `CredentialStore` and refresh

**Anthropic: go.** Evidence: [`q3-anthropic-turn.json`](spi-1161/q3-anthropic-turn.json).
- `Models.complete` on `claude-haiku-5-5`, with the OAuth credential in a DO-backed `CredentialStore`.
- Step 1 called `add({a:1234,b:4321})` (1.1 s). Step 2 answered `5555` (1.9 s, a 539-token cache read).
- pi-ai's OAuth mode took effect: Bearer auth, the oauth beta, and the Claude Code identity block.
- Response headers include Anthropic's unified rate-limit headers (`anthropic-ratelimit-unified-*`: overall and 7-day status,
  utilization, reset). These can feed the Usage page and limit meters.

**Codex backend: no-go from a Worker.** Evidence:
[`q3-codex-turn-sse.json`](spi-1161/q3-codex-turn-sse.json), [`q3-codex-turn-ws.json`](spi-1161/q3-codex-turn-ws.json),
[`q4-codex-header-matrix-worker.json`](spi-1161/q4-codex-header-matrix-worker.json),
[`q3-codex-backend-laptop.json`](spi-1161/q3-codex-backend-laptop.json),
[`q3-codex-backend-container.json`](spi-1161/q3-codex-backend-container.json).
- **From the agents Worker:** every request to `chatgpt.com/backend-api/codex/responses` got a **403 Cloudflare
  challenge page** (`text/html`, `set-cookie`, `cf-ray`). That held for pi-ai's SSE and WebSocket settings, and for
  every header combination in the matrix.
- **From the laptop** (docker, residential egress) with the same Free-plan token: `200` and `response.completed` for
  `gpt-6-luna` and `gpt-5.6-luna`, and `GET /codex/models` was 200. **So the Free plan is entitled to the Codex
  backend.** The 403 comes from the Worker's egress, not the plan.
- **From the Workspace Container** (direct egress, ATL), an unauthenticated POST reached OpenAI's origin (`401
  {"detail":"Unauthorized"}`, JSON), not a challenge. A Container can reach the Codex backend.
- **Refresh through the store** ([`q5-*-refresh.json`](spi-1161/)): with the stored expiry forced to the past, two
  concurrent `Models.getAuth` calls made **exactly one** refresh write. pi-ai's lock held over our DO-backed store, for
  both vendors, and a turn made no store writes.

**What the Codex tickets must decide (escalation):** a Durable agent's ChatGPT turns, and the relay's Codex route,
cannot call `chatgpt.com` from a Worker fetch. They need non-Worker egress: the Workspace Container's, or another
egress the owner picks. The token never needs to enter the Container, because the relay can open the upstream
connection from a process outside the agent's sandbox. But some always-reachable non-Worker hop is required.

## Q4. A Worker pass-through that swaps a handle for the real credential

**The setup:**
- Each CLI ran in docker `ubuntu:26.04` (arm64, Codex's musl binary, Claude Code from npm), holding only a 32-byte
  handle (`t3h_…`).
- The Worker route looked up the handle's SHA-256 in the probe DO, got the current access token from
  `Models.getAuth` (which refreshes when near expiry), and set `Authorization: Bearer <token>`.
- It dropped the client's `authorization`, `x-api-key`, `host`, `cf-*` and `content-length` headers, and streamed the
  upstream body back through a timing `TransformStream`.

**Claude Code to Anthropic through the Worker: go.** Evidence:
[`q4-claude-code-worker-relay.json`](spi-1161/q4-claude-code-worker-relay.json).
- **Config:** `ANTHROPIC_BASE_URL=<host>/api/probe1161/relay/anthropic` and `ANTHROPIC_AUTH_TOKEN=<handle>`. Claude
  sends it as `Authorization: Bearer`, and reports `apiKeySource: none`.
- **Tool turn:** 69 s wall time over 6 model requests, with idle gaps from two `sleep 25` Bash steps.
- **Single long stream:** `claude-sonnet-5-5` at high effort ran **90.8 s in one response** through the Worker (276 KB,
  longest gap 1.6 s, first byte 0.4 s).
- **What Claude Code sends:**
  - `user-agent: claude-cli/2.1.322 (external, sdk-cli)`.
  - `anthropic-beta`: `interleaved-thinking-2025-05-14, context-management-2025-06-27, claude-code-20250219,
    per-turn-control-2026-07-01, mid-conversation-tool-changes-2026-07-01, thinking-token-count-2026-05-13,
    advanced-tool-use-2025-11-20, effort-2025-11-24, thinking-display-updates-2026-08-18`. It does **not** send
    `oauth-2025-04-20`, because it thinks it holds an API key.
  - Its own Claude Code system prompt.
- **What the relay must add:** `Authorization: Bearer <oat>`, and `oauth-2025-04-20` appended to `anthropic-beta`.

**What Anthropic needs with an OAuth token**
([`q4-anthropic-header-matrix.json`](spi-1161/q4-anthropic-header-matrix.json)):

| Request | Result |
|---|---|
| Bearer + `oauth-2025-04-20` + a system prompt starting "You are Claude Code, Anthropic's official CLI for Claude." | 200 |
| Same, without that system prompt, or with another one | **429 `rate_limit_error` "Error"**: a disguised refusal, not a real rate limit |
| Same, plus `claude-code-20250219`, a `claude-cli` user agent and `x-app: cli` | 200 (none of these is needed) |
| The token sent as `x-api-key` | 401 `invalid x-api-key` |

So a relay for any client other than Claude Code (OpenCode, pi, a generic Anthropic client) must make sure the first
system block is the Claude Code identity, as pi-ai does. Claude Code sends it itself.

**Codex CLI to ChatGPT's Codex backend through the Worker: no-go** (the same challenge,
[`q4-codex-worker-relay.json`](spi-1161/q4-codex-worker-relay.json)). The Codex config used:
`model_providers.relay={base_url="<host>/api/probe1161/relay/codex", wire_api="responses", env_key="T3H",
requires_openai_auth=false, supports_websockets=false}`. Codex sent its handle as a Bearer token, and `turn.failed`
with the 403 HTML.

**The same swap from non-Worker egress: go.** Evidence:
[`q4-codex-offworker-relay.json`](spi-1161/q4-codex-offworker-relay.json). A node relay in a second docker container
on the laptop stood in for the Container's egress.
- **Tool turn:** 75 s over 4 requests, with idle gaps from two `sleep 25` steps.
- **Single long stream:** high reasoning ran **123 s in one response** (1.6 MB, 6,780 output tokens including 1,621
  reasoning tokens, one idle gap of 5.0 s), ending with the marker.

**What the Codex CLI sends:**
- `originator: codex_exec` and `user-agent: codex_exec/0.167.2 (…)`.
- `session-id`, `thread-id`, `x-client-request-id`, `x-codex-window-id`, `x-codex-beta-features`,
  `x-codex-turn-metadata` (a JSON holding the installation, session and turn ids, the model and the sandbox mode),
  and `x-openai-internal-codex-responses-lite`.
- **The body** carries `client_metadata, include, input, model, parallel_tool_calls, prompt_cache_key, reasoning,
  store (false), stream (true), text, tool_choice`, about 52 KB for a first request.

**What the Codex backend needs** (matrix from the laptop): only `Authorization: Bearer`. `chatgpt-account-id`,
`originator` and `OpenAI-Beta` were each optional for this one-workspace account. The relay should still set
`chatgpt-account-id` from the token's claim, because an account in several workspaces needs it to pick one; pi-ai
always sends it.

**Streaming and idle gaps:** neither relay buffered. A Worker kept a 91 s response open with no limit hit, and gaps
between requests (25 s and more) cost nothing, because each request is its own fetch.

## Q5. Refresh-token rotation

Evidence: [`q5-anthropic-refresh.json`](spi-1161/q5-anthropic-refresh.json),
[`q5-anthropic-replay.json`](spi-1161/q5-anthropic-replay.json),
[`q5-openai-codex-refresh.json`](spi-1161/q5-openai-codex-refresh.json),
[`q5-openai-codex-replay.json`](spi-1161/q5-openai-codex-replay.json).

| | Anthropic (Claude OAuth) | ChatGPT (`openai-codex`) | Copilot |
|---|---|---|---|
| Access token lifetime | 8 h (`expires_in` 28800; pi-ai stores it 5 min short) | 10 days (`expires_in` 864000; the JWT's `exp − iat` agrees) | untested. In pi-ai's code, the Copilot token comes from `copilot_internal/v2/token` with its own `expires_at`, and the GitHub OAuth token serves as the refresh token and never rotates. |
| Refresh frequency (pi-ai refreshes at < 5 min left) | about every 8 h of use | about every 10 days | — |
| Does the refresh token rotate? | **Every refresh** | **Every refresh** (its length changed 196 → 211) | — |
| The replaced refresh token presented again | **Rejected**: `400 invalid_grant` "Refresh token not found or invalid". The current token still worked afterwards: no family revocation. | **Accepted**: it rotated again, and the current token also still worked. Reuse is tolerated at least seconds after a rotation. A longer window was not tested. | — |
| Cost of a lost rotation (refreshed at the vendor, but the new token never saved) | **The stored refresh token is dead, and the owner signs in again.** The access token from that refresh is lost too. | Probably recoverable within a short grace window. Beyond it, unknown, so treat it as signing in again. | — |
| Refresh-token lifetime | The token response gives `refresh_token_expires_in` (its value was not recorded) | Not stated | — |

**What this means for the sign-in tickets:** the Environment DO as the only refresher (ADR-0018) matters most for
Claude.
- Write the refreshed credential to storage **before** answering any caller. pi-ai's `refreshStoredOAuthCredential`
  does this inside `modify`, so the DO's `CredentialStore.modify` must commit before it resolves; the probe's did.
- Nothing may refresh outside that lock.
- A deploy that resets the DO between Anthropic's answer and the write costs a sign-in.

## Sign-out

Evidence: [`finish-logout-*.json`](spi-1161/).

| Account | Revoked at the vendor? |
|---|---|
| ChatGPT (`openai-codex`) | **Yes.** I POSTed both tokens to the revocation endpoint from discovery, `https://auth.openai.com/api/accounts/oauth/revoke` (form: `token`, `token_type_hint`, `client_id`), and got 200 for each. A refresh afterwards failed with `401 "Your session has ended"`. |
| Claude | **No, it could not be revoked.** `platform.claude.com/v1/oauth/revoke` answers 404, and `console.anthropic.com/v1/oauth/revoke` serves a Cloudflare challenge to a Worker. A refresh after both attempts still succeeded; that refresh issued a new pair, which was then discarded unsaved. **The owner should revoke the grant in claude.ai** (Settings, connected apps or sessions), or let it lapse. The sign-in tickets have no API sign-out for Claude: deleting the stored credential is all they can do. |
| GitHub (Copilot device grant) | **No, it could not be revoked.** GitHub revokes an OAuth app's token only with that app's client secret. **The owner should revoke "GitHub Copilot" under github.com → Settings → Applications → Authorized OAuth Apps.** No Copilot token was issued. |
| ChatGPT token sharing | No tokens were issued. Each approval registered a dynamic client (`oaiapp_…`); the owner may remove those under ChatGPT's connected apps if they are listed. |

The probe's storage was cleared, and the stage was destroyed with it. Every local file that held a handle or token
(0600, under `/tmp`) was deleted, along with the relay container, and every pasted code file was deleted after use.

## Escalations

1. **ChatGPT's Codex backend refuses Worker egress.** This affects SPI-1164 (the ChatGPT sign-in for the Durable agent)
   and the Codex route of the relay (SPI-1167 onwards). Durable ChatGPT turns and the relay's Codex route need
   non-Worker egress. My recommendation: send Codex-backend requests out through the Workspace Container's egress, with
   the token added outside the agent's process. The other option is to drop ChatGPT for Durable agents.
2. **ChatGPT token sharing** (`api.openai.com`) is unsettled: Free plan or Worker. Recommendation: defer it, and
   recheck with a paid plan.
3. **Copilot** is untested (its subscription has ended). The device flow itself runs in the Worker.
4. **Claude has no API sign-out.** The panel's "Sign out" can only forget the credential, and should send the owner
   to claude.ai to revoke.

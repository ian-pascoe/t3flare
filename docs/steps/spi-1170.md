# SPI-1170: The pi CLI through the model relay

pi CLI threads run on every Model endpoint through the model relay (SPI-1167), with the process's model handle as
each provider's key. Decision record: [ADR-0016](../adr/0016-no-vendor-credential-enters-a-container-and-cli-agents-reach-the-model-proxy.md)'s
SPI-1170 refinement; [ADR-0034](../adr/0034-model-endpoints-are-the-owners-set-in-the-harness-panel.md) items 6 and 7;
fragility [U77](../upstream-fragility.md#u77-pi-on-model-endpoints-through-the-model-relay-spi-1170).

## How pi handles several endpoints

pi takes **a base URL per provider** (`models.json`), and several providers per process, like OpenCode. So each
endpoint is its own pi provider, `t3flare-endpoint-<endpointId>` (`endpointProviderId`, so no endpoint id changes one
of pi's built-in providers such as `openai` or `google`), with the endpoint's API and the relay's **per-endpoint URL**
as its base URL. The model-routed URL is not used. A model switch between endpoints, across APIs, stays in the
thread's process and its native pi session (p1170, and five APIs in `test:docker`).

**Which APIs.** All five. pi is pi-ai's coding agent, and an endpoint's API is by definition one pi-ai speaks
(ADR-0034); its base URL follows pi-ai's convention, so pi-ai appends each API's own path to the relay URL exactly as
it would to the endpoint's. None is left out.

| API | Path at the relay | Key header (pi-ai's) |
| -- | -- | -- |
| Anthropic Messages | `…/t3flare/model/<id>/v1/messages` (`?beta=true`) | `x-api-key` |
| OpenAI Responses | `…/<id>/responses` | `authorization: Bearer` |
| OpenAI-compatible Completions | `…/<id>/chat/completions` | `authorization: Bearer` |
| Google Generative AI | `…/<id>/models/<model>:streamGenerateContent?alt=sse` | `x-goog-api-key` |
| Mistral | `…/<id>/v1/chat/completions` | `authorization: Bearer` |

Each key header is in the relay's `KEY_HEADERS`. Measured in `test:docker` (all five) and on p1170 (the first three).

## How pi resolves a provider's key (pi 1.5.2, read at the pin)

`models.json`'s `apiKey` is a literal, a `$NAME`/`${NAME}` interpolation, or a `!command`
(`dist/core/resolve-config-value.js`, `docs/models.md`):

- **`$NAME`** reads `process.env` (`resolveEnvConfigValue`, line 71). It would need the handle in pi's environment,
  which pi's bash tool and every command it runs inherit. Not used.
- **`!command`** runs the command through a shell with pi's environment and takes its stdout. For an API key it is
  **not cached and re-resolved per request**: `composeApiKeyAuth`'s `resolve` (`dist/core/provider-composer.js:295`)
  calls `resolveConfigValueOrThrow`, which calls `resolveConfigValueUncached` (`resolve-config-value.js:192`, unlike
  the cached `resolveConfigValue` used for headers); `ModelRuntime.prepareRequest` (`dist/core/model-runtime.js:459`)
  resolves the auth for every stream. The availability check (`check`, `provider-composer.js:270`) does not run the
  command, so pi runs it only when it sends a request. Used: `apiKey: "!/opt/t3flare/bin/t3flare-pi-handle"`.

## Where the handle is (the brief's question)

The Workspace DO puts the handle in the process's environment (`T3FLARE_MODEL_HANDLE`), as for the other CLIs. The
launch chain is `setsid --wait /opt/t3flare/bin/pi --mode rpc …` (the process command's) → the launcher, which execs
the image's Node running pi **without** the handle (`env -u`). So pi's process does not hold it, and nothing pi
starts (its bash tool's commands, its built-in MCP's servers, `!command`s) inherits it. No file holds it: the
`models.json` names the command, not the handle.

`t3flare-pi-handle` (the `!command`) walks up from its parent (pi's shell, then pi) to the first process whose command
line starts `setsid --wait /opt/t3flare/bin/pi`, and prints its start environment's handle only when that process's
marker (`T3FLARE_EXEC`) is the command's own; otherwise it prints nothing and fails, pi sends no request ("Failed to
resolve API key … from shell command"), and the turn fails closed. Because it walks its own ancestry, a command that
sets `T3FLARE_EXEC` to another pi process's marker gets nothing, and neither does a command outside any pi launch
chain (both run in `ubuntu:26.04` and Debian with a stand-in chain; the second on p1170 too).

**What this does not do.** It keeps the handle out of environments and files, not out of reach of the Container's
commands. setsid's start environment holds it, readable by any process of the same uid, and everything in the
Container is root. A command pi's bash tool runs is in pi's launch chain, so it can run `t3flare-pi-handle` (or read
setsid's `/proc/<pid>/environ`) and spend through the handle, for that process's endpoints, until the process exits.
The same class as Codex's, Claude Code's (whose Bash can run its handle helper) and OpenCode's, not wider; no command
can take an endpoint's key out of the Container (ADR-0016's residual).

**Where the handle can go** (the brief's redirection question). The handle goes into a request to the model's
`baseUrl`, which pi takes from the model's `models.json` entry, else its provider's (`modelFromJson`,
`provider-composer.js:88`), or from an extension's `registerProvider` (which wins). What can set either:

- **`models.json`** is read only from the agent directory (`model-runtime.js:81`, `agent-session-services.js:59`):
  `PI_CODING_AGENT_DIR`, the process's own fresh home (`0700`, root's). pi has no project `models.json`. The profile
  pins `api` and `baseUrl` on every model as well as on the provider.
- **Extensions and packages**: only t3's extension is passed (`--extension`, checked against t3's source). A
  repository's `.pi/extensions`, `.pi/settings.json` (`extensions`, `packages`, `defaultProjectTrust`) and project
  `mcp.json` load only under project trust, which `defaultProjectTrust: "never"` and `--no-approve` keep off.
  `test:docker`'s hostile repository has all of these, plus a `.pi/models.json`: its extension never loaded and no
  request went anywhere but the relay.
- **`modelOverrides`** cannot set a `baseUrl` (its schema has none).
- **pi's environment** is the profile's allowlist; a repository cannot set a proxy variable in it.
- **A root command in the Container** can rewrite the home's `models.json` (pi rereads it only on a reload). Such a
  command can already read the handle (above).

So, unlike OpenCode (SPI-1169 round 1), no repository configuration reaches pi's provider settings: the handle goes
only to the relay's URL for that endpoint, and no placeholder or request-time hook is needed. pi's built-in providers
with an endpoint's name are never reached by t3: an endpoint id in a `set_model` is mapped to its prefixed provider.

Proved on p1170: the only process whose environment holds the handle is `setsid --wait /opt/t3flare/bin/pi --mode rpc`;
pi's own process (setsid's child, titled `pi`) does not; no file in `/var/lib/t3flare`, `/root`, `/tmp` or
`/workspace` holds it; a full-access turn's `env > file` has `T3FLARE_EXEC` and no handle; the handle command run
from the admin route's shell (not a pi launch chain) prints nothing. `test:docker` checks the same with the real image
layer (holders, a bash tool command's environment; with the launcher's `env -u` removed, it fails). The handle command
and the launcher's `env -u` were also run in `ubuntu:26.04` (uutils coreutils 0.10.0) and `node:26.13.0-bookworm-slim`.

## Models in t3's picker

- **Where they come from.** pi's snapshot lists `piModelsOf`: with an endpoint that lists a model, those endpoints'
  models by slug (`<endpointId>/<modelId>`), grouped by endpoint (its id beside a label two endpoints share), pi's
  `thinking` picker on reasoning models, the first marked default; else the proxy's catalog. It refreshes on every
  endpoint change (`refreshOnEndpointsChanged`, now wired for pi). p1170 listed exactly the 3 endpoint models.
- **t3's slugs and pi's provider ids.** t3's Pi adapter names a model to pi as `{ provider, modelId }` (`set_model`,
  splitting the slug at its first `/` unless pi reported the pair), and reads pi's back (`get_available_models`,
  `get_state`, an assistant message's `provider`). On the relay, the process's RPC lines are mapped at the channel
  (`cliProcess.ts`): a `set_model` naming an endpoint id names its `t3flare-endpoint-<id>` provider; in pi's responses
  and `message_end` events, a `provider` member naming an endpoint's provider names the endpoint id. Lines are parsed
  only when they can hold one; everything else passes byte for byte. So t3 sees its own slugs throughout (the session
  model, the provider turn's reported model, the context window), and pi's session file keeps pi's ids, which follow
  from the endpoint's id, so a session resumes in a new process (p1170, `test:docker`).
- **The proxy's models.** Following the accepted per-Environment choice (escalation 1): with an endpoint that lists a
  model, every pi process runs on the endpoints, and the proxy's provider is not configured. t3's registry does not
  keep a ready `pi` snapshot's missing models (`ProviderRegistry.ts` `shouldRetainMissingProviderModels`), so the
  proxy's leave the picker (p1170: `proxyRetained` 0).
- **Stale ids.** A thread on an earlier proxy model (`anthropic/<id>`) sends `set_model` for pi's built-in
  `anthropic` provider, which has no key here: pi refuses it ("Model not found: anthropic/<id>", `test:docker`) before
  any request, and t3 fails the turn. An endpoint that is gone is the same. Not mapped to another model until
  SPI-1176's fallback.
- **The model pi starts on** (`settings.json` `defaultProvider`/`defaultModel`): the picker's default, so t3's
  `default` model (`PI_INHERIT_MODEL_SLUG`) is an endpoint's model too.

## Headers

From the relay's log (names only), pi's requests drop: `accept-encoding`, `accept-language`,
`anthropic-dangerous-direct-browser-access`, `connection`, `host`, `session-id`, `user-agent`, `x-client-request-id`,
`x-stainless-*`, and `x-api-key`/`authorization` (the handle). In `test:docker` pi also sends Google's
`x-goog-api-client` and Mistral's `x-affinity`, which the allowlist drops too (Google's and Mistral's APIs forward only
the shared headers, `forwardedHeadersOf`), and `x-goog-api-key` (the handle). None routes or is needed: every pi request on p1170 was 200
(16 of them). `session-id`, `x-client-request-id` and `x-affinity` are prompt-cache affinity hints (pi's
`sessionAffinityFormat`), which a gateway behind the relay could use to pick a replica; dropping them costs at most
cache hits. **The allowlist is unchanged.**

## Escalations (provisional, as assumed)

1. **The relay-or-proxy choice is the Environment's for pi too**, as the brief directs from SPI-1168's accepted choice:
   with any endpoint that lists a model, every pi process is on the endpoints and the proxy's models are refused in pi
   threads (ADR-0034 item 6). Unlike Claude Code's and OpenCode's, pi's configuration is per process (its home), so a
   per-session choice would be possible; the Environment's rule was kept so the CLIs behave alike until the hard cut.
   Recommendation: accept (the owner adds Commissary as an endpoint, as the stage does).
2. **pi gets every endpoint API**, Google Generative AI and Mistral included. They are proved against `test:docker`'s
   stand-in only (their paths and key headers are pi-ai's own); the stage proves Anthropic Messages and OpenAI.
   Recommendation: accept; a real Google or Mistral endpoint on a stage when the owner has a key.
3. **t3's slugs are mapped on pi's RPC lines** at the channel (`set_model` in, `provider` members of responses and
   `message_end` out), as Codex's guard rewrites its protocol. The alternative, pi provider ids equal to endpoint ids,
   would let an endpoint named `openai` or `google` change pi's built-in provider of that name (its built-in models
   and stream functions). Recommendation: accept. If pi adds another RPC field that carries a provider and t3 reads
   it, it shows pi's id (`t3flare-endpoint-<id>/…`) until mapped (U77).
4. **pi's bash can print the handle** by running `t3flare-pi-handle`, as Claude Code's Bash can run its helper; a
   forged marker does not help (the command walks its own ancestry). The same exposure class, not wider.
   Recommendation: accept.
5. **A stale proxy model fails the turn** with pi's "Model not found: anthropic/<id>" (no request is made). Not mapped
   to another model until SPI-1176's fallback, as for Claude Code and OpenCode.
6. **pi's failure texts for a relay 401** are pi's own ("… 401 …" from pi-ai); none names the Model proxy's key. Left
   to SPI-1171's failure rework if it wants an endpoint-specific text.
7. **An endpoint added while a pi process runs** is in its handle's scope and `models.json` only from its next
   process (403 until then, measured with `canary`), as for the other CLIs.

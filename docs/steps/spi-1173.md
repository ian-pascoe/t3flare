# SPI-1173: The Usage page from t3flare's own usage records

t3's Usage page now reads t3flare's own **usage records** (`GLOSSARY.md`): every model answer on a Model endpoint,
counted where t3flare sees it, kept by the Environment DO, and served through t3's usage readers. Until the hard cut
(SPI-1176) the page also reads Commissary's request log, which alone sees the Model proxy's traffic; no request is
counted by both (below). Fragility: [U79](../upstream-fragility.md#u79-the-usage-page-from-t3flares-own-usage-records-spi-1173),
with U58 and U11 brought up to date.

## Where a record is made

| Seam | What it reads | Where |
| -- | -- | -- |
| **Durable** | Each final assistant message of an endpoint provider's model (turns, compaction, the extensions' own calls: all go through the Session's models): pi-ai's `usage` and `cost.total` | `apps/agents/src/session/models.ts` (`answering`, `EndpointAccess.answered`), `session/endpoints.ts`, `SessionDO.ts` |
| **Text generation** | Its one answer's pi-ai usage, under `text-generation` | `endpointText.ts`, `endpointTextGeneration.ts` |
| **Relay** | Each CLI request's answer as it streams past: the final stream event or the body, per API (below) | `apps/agents/src/workspace/relayUsage.ts`, wired by the `usage` dep of `modelRelay.ts`, in `workspaceProxy.ts` |

All three send through one helper, `usageSender` (`apps/agents/src/environment.ts`): the Environment DO's
`recordUsage` RPC (never boots t3) in `ctx.waitUntil`, after the answer. A failed send loses that record and is
logged by names only. Each recorder's `usage` option is required, so a recorder left unwired does not typecheck. The
record type is `@t3flare/models/usage` (`UsageEntry`; the counts through one `tokensOf`, the cost through
`positiveCost`): agent, endpoint id, model id, time, an opaque session (a Session's id, a CLI process's key), the token
counts and the cost when known. **No key, handle, prompt or answer text**: the relay reader keeps counts and the
model's name and drops the text as it reads.

### The relay's reader

A pull-through stream: each chunk goes to the CLI first, then a copy is read, an SSE stream line by line (only `data:`
lines holding `"usage` or `"model` are parsed), a JSON body whole once it has ended (Google's streamed JSON array
included). Nothing waits on the reader, and any failure in it stops the reading, never the answer. A line or body over
4 MiB stops it (the test caught the cap missing a line's last piece; fixed). A stream the CLI cancels, or that fails
upstream, is recorded once with what was read (Anthropic's input is in its first event); a cut JSON body is not.

| API | Usage taken from |
| -- | -- |
| Anthropic Messages | `message_start`'s message (model, input, cache read, cache write), the last `message_delta` (output); a body's `usage` |
| OpenAI Responses | `response.completed` (or `.incomplete`, `.failed`)'s response (`input_tokens` less `cached_tokens`, `reasoning_tokens`) |
| Chat Completions | the last chunk's `usage` (`prompt_tokens` less `cached_tokens`) |
| Google | the last `usageMetadata` (thoughts counted into output; `modelVersion`) |
| Mistral | `conversation.response.done`'s usage, or Chat Completions' shape |

**Chat Completions' usage is sent only when asked for** (`stream_options.include_usage`). Both CLIs that speak it ask:
pi through pi-ai (`dist/api/openai-completions.js:568`, unless a model's compat sets `supportsUsageInStreaming:
false`), and OpenCode 2.2.7 (`packages/ai/src/protocols/openai-chat.ts:900` at tag `v2.2.7`, unless a model sets
`streamUsage: false`, which our system configuration does not). The relay adds nothing to a request; a CLI that stopped
asking would go unrecorded on that API (U79).

The model is the request's own id when it named one to the relay (Claude Code's model-routed requests), else the
answer's; the Environment maps a **dated** answer name to the endpoint's listed model (`-YYYYMMDD` or `-YYYY-MM-DD`
only: `claude-x-20250929` is `claude-x`, `gpt-5-mini` is not `gpt-5`). The agent is the process's CLI (`codex`,
`claude`, `opencode`, `pi`); the stage's `probe` is not recorded.

## Beside Commissary's log, never twice

The orchestrator's decision on escalation 1 keeps Commissary's log on the page until SPI-1176. It alone has the Model
proxy's traffic: Durable turns on `anthropic/…` models, **web search** (`extensions/web/search.ts:164`, a request on
`MODEL_PROXY_API_KEY`), **prompt suggestions** (`SessionDO.ts`'s `#suggestionModels`, `proxyModels` on the same key),
the Environment's text generation on proxy models, CLI agents through the key helper, and all history before this
change. Each is on the proxy's key, a principal the log is read for, so each stays counted, by the log.

The double count is stopped at the Environment, where the keys are: `recordUsage` drops the records of every endpoint
whose API key is a principal Commissary's log is read for (`usage/records.ts` `countedByCommissary`: `key:<id>` of a
`cms_` key, the proxy's own or one in `COMMISSARY_USAGE_PRINCIPALS`; only when the management API is configured). It
opens the sealed keys once per revision of the endpoints (every save, a key's included, makes a new one;
`commissaryCountedCache`), and nothing leaves the Environment. When it cannot tell, it drops the records: a missing
record over a doubled one. The Sessions and the relay record as for any endpoint; only the Environment decides, so the
decision always follows the key the endpoint has now. Why not filter the log instead: its records name a principal,
not an endpoint, so one key's endpoint traffic cannot be told from its proxy traffic there.

**For SPI-1176**: this exclusion goes with the Commissary readers (`usage/readers.ts`' log half, `commissary.ts`'s usage
part, `countedByCommissary`, `commissaryCountedCache`); from then on every endpoint, Commissary's included, is counted
by our records alone.

## Storage (the Environment)

`apps/environment/src/usage/records.ts`, a table in the Environment DO's SQLite:

- **Rolled up as written**: one row per quarter hour, agent, endpoint, model, session and whether the cost is known,
  holding the sums. The page buckets by hour at the finest, so nothing it shows is lost, and the quarter hour keeps the
  half- and quarter-hour time zones on the right day. A busy session makes one row a quarter hour, not one a request,
  so a read of the page's widest window stays small in a 128 MB isolate.
- **Retention: 92 days**, t3's own `CACHE_RETENTION_DAYS` (the longest t3 keeps a transcript's usage, more than the
  page's widest range of 90 days), **and at most 50,000 rows**, oldest first, a guard against a runaway writer (a heavy
  owner makes a few hundred rows a day). Both are pruned on a write, at most once an hour.
- **Cost**: the Session's (pi-ai's, from the endpoint's model prices) when positive; else, for a relayed answer, the
  endpoint's listed model's prices; else none. A row's `UsageRecord` then has `reportedCostUsd: null` and `rateModel`
  the model's own id, so **t3's rate table prices it** (`usagePricing.ts`).

## The Usage page

`usage/readers.ts` `usageReader`: one scan reader per t3 usage provider (typed by `UsageProviderKind`, in the Shadow's
`BUILT_IN_USAGE_DRIVERS`), reading our records, one source per agent (`t3flare://usage/<agent>`), then Commissary's log.
t3's provider kinds are a closed list, so the Durable agent, text generation and the pi CLI are all **Pi**; their
sources tell them apart (each bucket carries its source path). A model is shown as its slug, `<endpointId>/<modelId>`,
so the same model on two endpoints is two rows. **The page's record counts are our rows** (a quarter hour of one
session on one model), not requests; tokens, costs and session counts are exact. The page shows them as t3 counts them:
saying so on the page would need a Patch, so it is documented here, in `records.ts` and in U79.

## Escalations

1. **Decided** (orchestrator): Commissary's log stays until SPI-1176, and our records of proxy-key endpoints are
   dropped (above). The Session no longer records its Model proxy answers. Consequence: on a proxy-key endpoint the
   page shows Commissary's attribution, in which relayed Claude Code and OpenCode requests count as Pi.
2. **The Durable agent, text generation and the pi CLI share t3's `Pi`** (t3's provider kinds are a closed list; a
   new kind would be a Patch of the contracts). Their sources tell them apart, which the per-provider rows do not show;
   the breakdown by model does.
3. **The page's record counts are rows, not requests** (above). Tokens, costs and sessions are exact.
4. **A relayed stream the CLI abandons** is now recorded with what was read (input from Anthropic's first event,
   OpenAI's and Google's usage only if it came before the cut). A cut JSON body is not recorded.
5. **Retention**: 92 days and 50,000 rows. Both are constants in `records.ts`.

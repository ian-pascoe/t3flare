# SPI-1152: Variables in Environment settings

Report for SPI-1152, a sub-ticket of SPI-1001's triage. The ticket is the plan. Decision record: the Variables
refinement in [ADR-0032](../adr/0032-environment-settings-and-harness-settings-are-separate-entities-edited-on-one-owner-page.md),
with a note in [ADR-0016](../adr/0016-no-vendor-credential-enters-a-container-and-cli-agents-reach-the-model-proxy.md).
Evidence: [`spi-1152/`](spi-1152/), from stage `pvars` (destroyed).

## What changed

- **One schema entry.** `ENVIRONMENT_SETTINGS.variables` in `@t3flare/harness-registry`, of a new field type
  `variables` (`{ NAME: "value" }`). `resolveEnvironment`, `ResolvedEnvironment`, the API's validation and the panel's
  section follow from it, as SPI-1149 set up. The new type lives beside the Harness settings' field types but only
  Environment settings may use it (`EnvironmentFieldSchema`), so the Harness settings' values stay scalars.
- **The rules** are in `packages/harness-registry/src/variables.ts`: the limits, the refused names (below), the refused
  values, and `fitVariables`, which reads a stored set against this Worker's rules. A stored Variable a later rule
  refuses is dropped alone; the rest of the set stays. A save that sends the same Variables in the same order moves
  nothing, as for the other settings.
- **Where they apply** (`apps/agents/src/workspace/variables.ts`, `WorkspaceDO.ts`).
  - The Container's launch record (`ContainerLaunch`) takes the Variables with the size, idle time and budget, so a
    running Container keeps the ones it started with.
  - One function, `commandEnv`, puts them under every other layer of a command's environment.
  - `VariablesBackend` wraps both of the Workspace's computer backends (the Container's and the Worker Shell's). It adds
    the Variables to each command computer sends, reading them as the command is sent: after computer has started the
    Container for it, so a command never runs with Variables its Container did not start with. That covers a Durable
    agent's commands on either backend and the Workspace DO's own commands.
  - Terminals, the agent's Terminals and CLI agent processes get them at spawn (`commandEnv` at the three
    `container.exec` calls), so a CLI agent's own commands inherit them.
- **The panel.** A Variables row in the Environment section's one form: a name and a value per Variable, Remove, and
  "Add a Variable". Saved with the section's Save, through the same route, guards and audit log. The script refuses a
  name listed twice before posting.
- **Audit.** The audit entry carries the Variables, names and values, before and after. The Workers Logs line stays
  without values (unit-tested).
- **Docs.** ADR-0032's Variables refinement; ADR-0016's note; `GLOSSARY.md`: **Variable** (new) and **Environment
  settings** (Variables added to its list). No t3 lean, so no `docs/upstream-fragility.md` entry: `VariablesBackend`
  wraps `@cloudflare/computer`'s exported `WorkspaceBackend` and `BackendHandle` types, not t3code.

## Readings and limits

- **The Session does not add Variables.** The ticket names `SessionDO.ts:608` as a merge point. A Session's command can
  be the one that starts the Container, and only the Workspace DO knows the Variables that start took. So the
  Workspace's backends add them instead, beneath `COMMAND_ENV` and `T3CODE_THREAD_ID`, which the Session still sends
  and which still win. The Worker Shell gets the last Container start's Variables, from the same record.
- **A Variable some layer sets is shadowed for that command only.** Rule 6 refuses every name t3flare sets, so this is
  left for t3's own variables on a spawn and a command's or mise's own.
- **The Worker Shell before any Container start** has no Variables: the record is written by a start.
- **Values are not secret-scanned beyond the patterns.** The guard is for the owner's mistakes (ADR-0016 A′), not
  against him.
- **Checks.** `pnpm run check` passes at `CHECK_COMMIT`.

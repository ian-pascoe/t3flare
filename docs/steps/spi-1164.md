# SPI-1164: the Credential broker and ChatGPT plan usage for the Durable agent

Stage `p1164`, 2026-11-16. Evidence is in [`spi-1164/`](spi-1164/). It holds no token and no code: the owner's pasted
redirect is recorded as `<redirect>` (its length and parameter names only), the authorize URL's state, nonce and
challenge by length, and OpenAI's issued client id as `oaiapp_<issued>`.

**Owner decision (2026-11-16), replacing the ticket's "device code":** ChatGPT signs in through "Sign in with ChatGPT"
plan usage, the spike's "token sharing" (SPI-1161 Q2). It calls OpenAI's public Responses API on `api.openai.com`, not
the Codex backend that `chatgpt.com`'s edge blocks for our Workers (SPI-1161 Q3). It is accepted that this may not work.

**State: built, tested against a fake OpenAI, and unverified against the real one.** On the owner's Free plan, OpenAI
refused the code exchange (`invalid_grant`), as the spike saw. No token was issued, so no turn ran on the subscription
(see [What is unverified](#what-is-unverified)).

## OpenAI's docs used, and where pi-ai differs

The flow follows OpenAI's own docs for open-source clients, read on 2026-11-16:

- [Overview](https://developers.openai.com/siwc/token-sharing-open-source): the client and the host id; plan usage is
  for "open-source and locally hosted apps", and a paid or remotely hosted app is asked to fill in an interest form.
- [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in): the authorize
  parameters, the 127.0.0.1 loopback redirect (only its port may vary), the issued `client_id`, the exchange at
  `https://auth.openai.com/api/accounts/oauth/token`, ID-token validation, and the required `chatgpt.tokens.use.direct`.
- [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions):
  reauthorizing with the saved client id, refresh (serialized, the replacement saved), and revocation at discovery's
  `revocation_endpoint`.
- [Token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference): access tokens last
  1 h; refresh tokens last 30 days and rotate.
- [Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery): the refresh
  codes that end a sign-in, and the `subscription_sharing_*` codes.
- [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference): `GET /v1/models`
  answers `{ models: [{ slug, display_name, visibility }] }`.
- [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations): `store: false`,
  `stream: true`, no `system` items, and the list of refused fields.

Where pi-ai 1.5.0's `openai-chatgpt` flow differs, OpenAI's docs were followed:

| | pi-ai 1.5.0 | Built (OpenAI's docs) |
|---|---|---|
| ID token | presence checked only | signature against OpenAI's JWKS, issuer, audience = issued client id, expiry, nonce |
| A later sign-in | always `dynamic_agent_client` | the saved issued client id, with `login_hint`; `agent_name_hint` on first registration only |
| Revocation | none | the refresh token at discovery's revocation endpoint, retried on 5xx |
| The attempt | in memory (`login()`) | sealed in the Environment DO, 30 minutes |
| Request rules | applied only when the provider is named `openai` | applied to every sign-in endpoint's request (`planUsagePayload`) |
| Refresh-ending codes | any error is a failure | OpenAI's codes sign the endpoint out; other failures keep a still-valid token |

## Seams tested

Every test of a sign-in runs against a fake of OpenAI's authorization server (`test/fixtures/fakeOpenAIAuth.ts`). The
fake covers discovery, an RS256 JWKS, the authorize step as a browser approval, the token endpoint with PKCE, and
rotating refresh tokens that refuse a replaced one. It also covers revocation, and it records every token it issues.

- **The sign-in client** (`chatgptSignIn.test.ts`):
  - The authorize URL carries OpenAI's parameters.
  - A saved registration's client id is reused.
  - A redirect pasted in full, without its scheme, or as the query alone completes.
  - Each failure is a fixed text without the code, verifier or tokens:
    - Free-plan `invalid_grant`;
    - another attempt's state;
    - declined consent;
    - no plan-usage scope;
    - not a URL;
    - another host.
  - An ID token for another nonce is refused.
  - Refresh rotates, and a replaced token is `invalid_grant`.
  - Revocation sends OpenAI's form.
- **The Credential broker** (`credentialBroker.test.ts`). Each test ends with a scan of storage and console output for
  every issued token.
  - It signs in, seals the tokens, and gives the token with its expiry.
  - **Concurrent refresh:** five callers inside the margin, with OpenAI held slow, cause **one** refresh.
  - **Rotation:** the stored refresh token is the replacement, and the next renewal succeeds with it.
  - **Saved before use:** if the renewed credential's write fails, no caller gets its access token.
  - **`invalid_grant` on refresh:** the endpoint is signed out with the reason, and a second ask makes no second refresh.
  - A passing failure keeps a still-valid token, then fails as retryable once it has expired.
  - **Sign-out:** it revokes, keeps the registration, and the next start reuses the client id.
  - A refused exchange is surfaced at once, and the spent attempt is dropped.
  - A mistaken paste keeps the attempt; a stale one lapses.
  - No credentials key means no start.
  - `modify` is serialized.
- **The panel** (`endpointsSignIn.test.ts`, the real `handleHarness`, store and broker):
  - The page offers the sign-in with the unverified, Plus-or-Pro note.
  - Start, then paste, saves a `chatgpt` endpoint with the models listed with its token.
  - The audit holds no token, and neither does the page, the answer or the console.
  - A Session gets the token only for the endpoint's target.
  - A Free-plan refusal comes back at once as JSON, with no endpoint saved, and stays on the page.
  - Sign-out revokes and stops the endpoint's Sessions.
  - Removing a signed-in endpoint signs it out.
  - A sign-in endpoint refuses a key, headers, another target, or a switch to a key.
  - An API-key endpoint's id is refused for a sign-in.
- **Stopping Sessions** (`signOutSessions.test.ts`): every open Session is told; only those on the endpoint abort; one
  that fails to answer is skipped.
- **The relay and the CLI profiles** (`endpointRelay.test.ts`, `codexEndpoints.test.ts`): a sign-in endpoint is refused
  (501) and not listed.
- **The turn's failure text** (`differ.test.ts`):
  - A signed-out endpoint's message is shown as written, ending at its own stop, with code `signed_out`, not retryable.
  - A passing failure is retryable.
- **The plan-usage model list** (`endpointDiscover.test.ts`).
- **The Session** (`apps/agents/test/sessionSignIn.test.ts`):
  - The token is sent as a bearer.
  - The body is `store:false`, `stream:true`, with none of the refused fields and `developer` in place of `system`.
  - **A turn spanning a token's expiry:** a token with 4 min left is kept for 1 min, then the same turn's request
    2.5 min in takes the refreshed one.
  - A 401 drops the token, and the next request asks again.
  - `drop` on sign-out.
  - A signed-out endpoint fails the request naming the sign-in, sending nothing; a passing failure names it too.
  - No token is in its storage.
- **Text generation** (`endpointText.test.ts`): a sign-in endpoint sends the bearer and the plan-usage body; a 403 names
  the sign-in and Plus or Pro; signed out, it sends nothing.
- **The storage scan in a real Durable Object** (`sessionEndpoints.workerd.test.ts`): a sign-in's token goes out as the
  bearer, and nothing in the object's KV or SQL holds it.

7. [`status-after.json`](spi-1164/status-after.json) and [`page-after.json`](spi-1164/page-after.json):

   - The audit has `endpoint.sign-in.start` and `endpoint.sign-in` `{ ok: false }`.

9. [`sign-out.json`](spi-1164/sign-out.json): sign-out answered `revoked: false`, since there was nothing to revoke.

## What is unverified

The ticket's criterion "a Durable turn with tools runs on the subscription on a throwaway stage" **is not met** and could
not be. The fake-vendor tests and the API-key stage turn stand in for it. Unverified against OpenAI:

- **A successful code exchange from a Worker.** It was refused twice in the spike and once here, each time on a Free
  plan. Whether a Plus or Pro plan succeeds, and whether OpenAI accepts the exchange from a remotely hosted Worker, is
  not known (escalation E1).
- **The ID token's checks against OpenAI's real token** (its `kid`, `aud` and `nonce` claims), and the real token
  response's `earliest_refresh_at`.
- **A refresh, a rotation and a revocation at OpenAI** for this flow.
- **A plan-usage Responses request with pi-ai's body**, especially its tools. OpenAI says to group function tools in
  namespaces or send them as `additional_tools`; pi-ai sends flat function tools, and t3flare sends them unchanged
  (escalation E2). The `/v1/models` shape is tested against the docs' example only.
- How plan usage's errors (`subscription_sharing_*`) read in a turn: they show as model errors. Classifying them per API
  is SPI-1172.

## Escalations

### 🙋 Need you

❓ **E1: Is a t3flare Environment a "locally hosted" app for OpenAI?** OpenAI documents plan usage for "open-source
and locally hosted apps", and asks a "paid or remotely hosted app" to fill in an interest form. An Environment runs on
the owner's own Cloudflare account; OpenAI may count it as remote. The options are: ship as built and unverified (the
owner's decision of 2026-11-16); also fill in OpenAI's interest form; or retest with a Plus or Pro account first.

➡️ Ship as built (the panel and the ADR say it is unverified and needs Plus or Pro), and leave the interest form to the
owner. D1 to D3 assume it.

❓ **E2: Flat tools or namespaced tools on plan usage?** OpenAI's preview page says function tools go in namespaces or
`additional_tools`; pi-ai sends flat `function` tools. Wrapping them would change how pi-ai reads tool calls back, and
nothing can be tested without a working sign-in.

➡️ Keep pi-ai's flat tools, record the risk, and recheck once a Plus or Pro sign-in exists.

### 👀 Worth a glance

- **D4** A refused renewal fails the next turn naming the sign-in, but does not stop other Sessions' turns; only an
  explicit sign-out stops them.
- **D5** The sign-in attempt waits 30 minutes for its paste. OpenAI does not document the code's life.

### 🌳 Decisions

- **D1** The broker: ours over the sealed store, implementing pi-ai's `CredentialStore` (types only). t3's
  `CodexChatGptAuth` was not used, because it is tied to t3's provider settings and secret store, which the panel's
  sign-ins do not use. → ADR-0018 refinement
- **D2** Refresh margin: 5 min (pi-ai's own), with access tokens lasting 1 h. The Session keeps a token at most 5 min
  and never past 2 min before its expiry, so it always asks after the broker would have renewed.
- **D3** A sign-in endpoint is created by completing a sign-in, not by the generic form. Its API, base URL and no
  headers are fixed. Its label and models stay editable ("Edit models"), and its auth never changes. A re-sign-in keeps
  the owner's model list.
- **D4** (above). A 401 drops the Session's token, and a sign-out drops it in every Session and aborts the turns on the
  endpoint (`signed_out`). The Environment tracks each open session's current endpoint from the adapter.
- **D6** The turn's failure text: a model error carrying our endpoint message shows that message, cut at its own last
  stop, so no vendor text follows it. This also makes SPI-1162's key messages ("changed or was removed", "no API key")
  reach t3, where they were shown as "The model provider reported an error."
- **D7** The relay and the CLI profiles exclude sign-in endpoints until SPI-1171. The relay answers 501.
- **D8** Redirect: `http://127.0.0.1:1455/auth/callback` always (OpenAI: only the port may vary; 1455 from the first
  registration). Host id: one `urn:uuid` per Environment, kept in its storage.
- **D9** The model list: plan usage's `models[].slug` entries with `visibility: "list"`, sorted by id as every other
  list is (OpenAI's example keeps the server's order).
- **D10** OpenAI's issued client id (a public identifier) is kept in the sign-in's status (the panel shows it; the audit does not). The evidence
  redacts it.

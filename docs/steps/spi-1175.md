# SPI-1175: Stages, acceptance and CI set up Model endpoints through the panel's API

Throwaway stages, the acceptance test and CI's deploy jobs now get a model without any `MODEL_PROXY_*` setting. After a
deploy, `stage.ts` saves a **Model endpoint** through the Harness panel's own API, and the acceptance test does the same
before its turns. On a laptop the endpoint comes from `dev.env`; in CI it comes from the GitHub secret
`T3FLARE_MODEL_ENDPOINT`, which `ci:setup` sets. The text-generation setting follows that endpoint's small model by
SPI-1163's default rule. The Model proxy stays optional beside it until the hard cut (SPI-1176).

## Owner steps (before the endpoint reaches CI)

Prod is recovered, so the order is: merge, then run `ci:setup`. Merging does not wait on `ci:setup`. Until the secret
exists, `deploy-prod.yml` and `bump.yml` log `t3flare: no Model endpoint set up: T3FLARE_MODEL_ENDPOINT is not set` and
carry on as today. The acceptance report then shows `modelEndpoint: { skipped: … }`, and the bump's real turn runs on
the proxy.

0. Merge this branch.
1. Optional: put your own endpoint in `~/.config/t3flare/dev.env` as `T3FLARE_MODEL_ENDPOINT='{"id":…,"baseUrl":…,"apiKey":…}'`
   ([format](../model-proxy.md#the-stages-model-endpoint)). Skip this to use Commissary's, made from `MODEL_PROXY_URL`
   and `MODEL_PROXY_API_KEY`.
2. From the main checkout, run `pnpm --filter @t3flare/infra run ci:setup`. From a worktree, add
   `T3FLARE_PROD_ENV_FILE=<main checkout>/apps/environment/.alchemy/stages/prod.env.json`. It sets the secret
   `T3FLARE_MODEL_ENDPOINT` on the GitHub environments `bump` and `prod`; no value is printed. With no
   `T3FLARE_MODEL_ENDPOINT` in `dev.env`, the derived JSON holds `MODEL_PROXY_API_KEY`: `ci:setup` then writes the
   Model proxy's key onto `bump` too (inside that secret), where until now it was only ever set by hand
   (`MODEL_PROXY_API_KEY`).
3. That's all. The next prod deploy adds the `commissary` endpoint to prod if prod has none with that id, and the next
   nightly bump runs its real turn on it.

## Escalations (assumed provisionally)

1. **One JSON secret, and a derived default.**
   - The endpoint is one setting, `T3FLARE_MODEL_ENDPOINT` (a JSON object holding its key), rather than one variable
     per field. One GitHub secret then carries everything, and `ci:setup` writes it.
   - Without it, a laptop and `ci:setup` derive Commissary's endpoint from the proxy's two settings.
   - SPI-1176 removes those settings, so at the hard cut the derivation goes and `dev.env` needs `T3FLARE_MODEL_ENDPOINT`
     itself. Recommendation: keep; SPI-1176 drops `commissaryEndpoint` and the `derive` branch.
2. **prod gets the endpoint only when it has none with that id**, and a deploy never changes it after that.
   - The owner's edits in the panel stand.
   - A rotated key reaches prod's endpoint only when entered in the panel.
   - A removed endpoint comes back at the next deploy while the secret is set.
   - When prod gets its first endpoint with a small model, its unset text-generation setting moves from the proxy's
     `anthropic/claude-haiku-5-5` to `commissary/claude-haiku-5-5` (SPI-1163's rule).

   Recommendation: keep. The alternative, saving on every deploy, would overwrite the owner's panel edits.
3. **The text-generation model is not written; it follows the default.**
   - An explicit write would read as the owner's pick, and the setting would stop following the endpoints (SPI-1163,
     U67). So `stage.ts` writes nothing, and the default sync names the endpoint's small model.
   - t3 resolves a selection on a provider that is turned off to its own fallback (Codex). Pi Durable is off on a new
     Environment until a client turns it on, so `stage.ts` alone leaves text generation resolving to Codex. The first
     acceptance run caught this.
   - `stage.ts` doesn't turn Pi Durable on, because that is a t3 setting and would need pairing (arming the bootstrap
     token on prod). The acceptance test and `p1175` turn it on as the client's onboarding does.

   Recommendation: keep. An admin route that turns Pi Durable on would be a new route, and out of this ticket's scope.
4. **A failed setup after a good deploy fails the command.** On prod that makes the job red and skips the smoke check.
   - It happens only on the first creation: after that, prod's setup is one `GET`.
   - An unusable secret fails before the Workers are built, so prod isn't deployed with it.

   Recommendation: keep. The alternative is a warning that nobody reads.
5. **`infra/github.ts` imports `apps/environment/scripts/lib/modelEndpointSpec.ts` by relative path.** The file has no
   dependencies. Adding `@t3flare/models` to infra would change the lock, and `relock` is broken (SPI-1206).
   Recommendation: keep.
6. **What a stage without the proxy still shows.** `alchemy.run.ts` binds neither setting; the agents Worker's
   `SessionEnv` still types them as strings.
   - The Session's catalog read fails quietly, and the static list stands.
   - The proxy's static `anthropic/…` models may still be listed, and fail when used (text generation says "The model
     proxy is not configured.").
   - Left to SPI-1176, which removes them.

### The evidence re-run, and an incident on prod's zone (recovered)

**Recovered by the orchestrator on 2026-11-15, and `p1175` destroyed.** The orchestrator restored prod's Access
application and rate-limit rule, emptied `p1175`'s state, and rotated prod's admin service-token secret (`32a23c6` on
`main`). This section is kept as the record of what happened.

Item 2 changes what alchemy is given, so I re-ran the evidence. To prove the shell-variable case, I deployed with
`dev.env` exported into the shell (`set -a; . dev.env`). That shell also exported **`T3FLARE_DOMAIN`**, prod's custom
domain, so `alchemy.run.ts` deployed `p1175` as if it were served at prod's host (`t3.ianpascoe.dev`).

What the logs show:

- **First attempt:** `AdminAccess` failed with "OwnedBySomeoneElse". I destroyed `p1175`, and alchemy left that
  resource in place ("exists in the cloud but is not owned by this stack").
  - I deleted that attempt's and that destroy's logs before the second attempt (`rm -f /tmp/p1175/*.log`), so what else
    they did is unknown.
- **Second attempt:** run with alchemy's `--adopt`, through an uncommitted one-off edit of `stage.ts`, since reverted.
  - The plan listed `[AuthRateLimit] adopted` and `[AdminAccess] create`; the apply logged `AdminAccess` "created".
  - Attaching `t3.ianpascoe.dev` to `p1175`'s Worker was refused ("already attached to Worker
    `t3flare-environment-prod`"), so the deploy failed. Nothing serves prod's host but prod.

**What the pinned alchemy source says happened.** This is from reading `@alchemy.run/cloudflare` and `alchemy`
2.0.0-beta.85 in `node_modules`. It is **not verified on Cloudflare**.

- **`AdminAccess` most likely took over prod's Access application; it did not create one.**
  - `Access/Application.ts`, `read`: with no stored id, it finds an application by its `domain` (`findByDomain`). It
    returns the result as `Unowned`, because Access applications carry no alchemy marker. Prod's application is on the
    same domain (`t3.ianpascoe.dev/_t3flare`). That is the first attempt's "OwnedBySomeoneElse".
  - The plan said `create` because the props held the new service token's id, an unresolved Output. `Plan.ts` skips
    the adoption probe for unresolved props and defers it. `Apply.ts` then runs it in the create path: it reads, finds
    the `Unowned` application, and with `--adopt` takes its attributes (prod's `applicationId`) as the output.
  - `reconcile` then sees that id (`observeById`) and **updates** prod's application in place, rather than creating
    one. The update replaces its name with `t3flare-environment-p1175 admin` and its inline policies with this stack's:
    the owner, and **`p1175`'s service token instead of prod's**. The log's "created" is the create lifecycle's word.
  - Consequences, if so:
    - Access on prod's `/_t3flare` now admits `p1175`'s service token and no longer admits prod's. CI's smoke check
      and every script that reaches prod's admin routes with prod's service token would be refused. Prod's admin token
      is still required behind Access.
    - `p1175`'s state holds prod's application id, and `delete` removes the application by that id. **Destroying
      `p1175` would delete prod's Access application.**
- **`AuthRateLimit` was adopted with no ownership check, and needed no `--adopt`.**
  - `Ruleset/Ruleset.ts`, `read`: returns the zone's phase entrypoint as plain attributes, never `Unowned`, so the
    engine adopts it silently. After an adoption, `Plan.ts` forces an update.
  - `reconcile` `PUT`s the whole phase entrypoint with this stack's rules: `ref: t3flare-auth-p1175`, a `p1175`
    description, and the same expression on `t3.ianpascoe.dev`, replacing prod's rule.
  - The first attempt may have done the same, and its destroy may have deleted that rule (`delete` removes the rules
    whose ids are in its output). With the logs gone, that is unknown.
  - Now: the zone's `http_ratelimit` entrypoint most likely holds `p1175`'s rule, owned by `p1175`'s state.
    **Destroying `p1175` would remove it**, leaving prod's host without the auth rate limit.
  - Prod's own next deploy diffs its stored props against its new ones (`diff` compares `olds.rules` and
    `news.rules`). It may see no change and not put the rule back. Unverified.

At the time, `p1175` could be neither destroyed nor deployed until prod's Access application and ruleset were
recovered; the orchestrator recovered them (above). Round 2 adds the guard that stops it happening again: `T3FLARE_DOMAIN`
is refused for any stage but prod.

**State: built and unit-tested; not verified against any subscription, by owner decision (2026-11-16): no live sign-in
for SPI-1171.** Unverified, therefore:

- **The live subscription matrix**: no CLI (Codex, Claude Code, OpenCode, pi) ran a turn on a ChatGPT, Claude or GitHub

- **The live mid-thread refresh**: no vendor renewed a token under a running CLI. The stage-only hook that would force

- **The live sign-out failure**: no signed-in endpoint was signed out under a CLI. What the stage shows instead is a

[`sign-in-start-*.json`](spi-1171/)) were abandoned by a sign-out, never completed ([`abandon.json`](spi-1171/abandon.json)).
No token was issued.

## The main risks (accepted provisional decisions)

1. **Tool names on a Claude sign-in** (decision 2). pi-ai gives a Session's tools Claude Code's names (`bash` → `Bash`)
   on a Claude subscription; the relay leaves a CLI's tools as the CLI names them (OpenCode's and pi's are lowercase),
   since renaming them would mean mapping them back in the answer's stream. If Anthropic refuses an OAuth request whose
   tools are not Claude Code's (a disguised 429, SPI-1161 Q4), OpenCode's and pi's turns on a Claude sign-in fail.
   Claude Code's own requests carry its own names and pass as they are.
2. **Codex's body on ChatGPT plan usage** (decision 3). Codex sends `client_metadata`, `include`, `prompt_cache_key` and
   flat `function` tools; plan usage's rules (the Session's `planUsagePayload`) drop the fields OpenAI lists, but its
   preview page wants function tools in namespaces or `additional_tools`. Codex's (and OpenCode's) flat tools may be
   refused.

Accepted too: ChatGPT is plan usage on `api.openai.com/v1` (SPI-1164's owner decision), not the Codex backend path the
ticket's wording names, which blocks our Workers (decision 1); Copilot is unit-tested only, live under SPI-1226
(decision 4).

## Seams tested

- **The CLI lists** (`codexEndpoints`, `claudeEndpoints`, `opencodeEndpoints`, `piEndpoints`, `cliProfiles` tests): each
  CLI lists, routes and configures exactly the ticket's sign-ins; pi's ChatGPT models carry plan usage's overrides.
- **The Environment's target** (`endpointRelay.test.ts`): a sign-in's token as a bearer, asked of the broker at every
  request (a renewed token is the next target's); a Claude token never as `x-api-key`; Copilot's token's base URL and
  editor headers only on a `githubcopilot.com` host; 401 signed out, 503 with `retryAt`; no broker is signed out.
- **The relay with a sign-in** (`apps/agents/test/modelRelaySignIns.test.ts`):
  - ChatGPT: the CLI's body by `planUsagePayload` (the Session's), the token as a bearer, no handle; a body plan usage
    takes passes byte for byte; each request's token is its own grant's (a mid-thread renewal), the short ids differ in
    the log; a body over the cap is 413 before anything is sent.
  - Claude: **pi-ai's own API-key-shaped request, sent through the relay, leaves it with the URL, headers, betas and
    system blocks pi-ai sends for the subscription's token** (`authorization`, `anthropic-beta`, `user-agent`, `x-app`,
    …); a CLI's own betas kept after Claude Code's; a system that already holds the identity left byte for byte;
    a model-routed request (Claude Code's) shaped after routing; a token echoed in an error redacted.
  - Copilot: the token's base URL, editor headers, `X-Initiator` (`user`, then `agent` after a tool's output),
    `Openai-Intent`, vision; no thinking-off `reasoning`.
  - No token: 401 in OpenAI's and Anthropic's shapes naming the sign-in, reported as `sign_in_refused`; a passing
    failure 503 with `retry-after`, reported as `unavailable`.
  Removing the relay's rules (the table's Claude and ChatGPT entries) fails five of these (checked).
- **The Workspace DO's check** (`modelRelayRoute.test.ts`): a sign-in's token remembered for the sync guard; a sign-in's
  refusal passed on with why.
- **The pins** (`claudeSignInShape.test.ts`): the Claude constants the relay uses equal pi-ai's wire.
- **The broker** (`claudeBroker.test.ts`): `secrets` gives the stored tokens without renewing, none signed out; a token
  marked expired by `expire` is renewed at the next use, once.
- **The leak check's names** (`endpointLeak.test.ts`): a sign-in's tokens read as stored, never through the relay's
  target.
- **The expire hook cannot ship enabled to prod** (`expireHook.test.ts`): it refuses (403) and touches nothing without
  the faults; every binding of `T3FLARE_FAULTS` in `alchemy.run.ts` is `...(stage === "prod" ? {} : { T3FLARE_FAULTS:
  "1" })`, and the Environment reads it as nothing but `"1"` (`environmentDO.ts`). A change that binds it for prod fails
  the test.
- **No sign-in's token from Workspace code** (`signInReach.test.ts`): still no `endpointCredential` caller there; the
  relay's target is the only way, and it ends in the agents Worker.

## Evidence on `p1171` (no subscription)

[`spi-1171/p1171.json`](spi-1171/p1171.json), from `scripts/p1171.ts control` through `stage.ts`: **22 checks, all
passed**, `head` 462e0dd (`clean: true`), the stage deployed from code identical to it (the run's later commits changed
the script only). Endpoints: the stage's `commissary` (Anthropic Messages, the proxy key), `resp` (Commissary's
Responses, the proxy key), and two sign-in endpoints saved with no credential, `sub-chatgpt` and `sub-claude`.

- **The lists follow the matrix**: Codex lists `sub-chatgpt`'s model and not `sub-claude`'s; Claude Code `sub-claude`'s
  and not `sub-chatgpt`'s; OpenCode and pi both.
- **A regression control per CLI**: a turn with tools through the relay on an API-key endpoint (Codex on `resp`; Claude
  Code, OpenCode and pi on `commissary`), approval-required, every request accepted: the file edited and `bash test.sh`
  run. (t3's projection of Codex's turn showed no file change or test-run item; the repo had the edit and Codex's
  answer the passing test, which is what the check reads.)
- **A sign-in that gives no token**: Codex's turn on `sub-chatgpt/…`, OpenCode's and pi's on `sub-claude/…` each failed
  with t3's failure `permission_error` / `sign_in_refused`: "The Model endpoint "sub-claude" is not signed in to Claude
  (it is not signed in): sign in with Claude again in the Harness panel." (ChatGPT's likewise). **Claude Code's** failed
  before any turn with t3's own "Failed to open claudeAgent provider session …", which names no sign-in: SPI-1172's E1
  (a refused credential at Claude Code's open is not a turn the CLI wrapper can map), unchanged here. A request at the
  relay with pi's process's handle got 401 on each sign-in, Anthropic's `authentication_error` for Claude, both naming
  the sign-in; the relay logged each as `sign_in_refused`.
- **The leak scan** in each CLI's Container, its processes alive: no key in the DO's files or the Container (611–747
  files, every process's environment and command line), nothing unscanned. A canary key planted in `/tmp` was found
  (the positive control). With no sign-in, there was no sign-in token to look for: the scan's sign-in names are
  unit-tested only.
- **The logs**: neither Worker's log (`wrangler tail`) held a key, a token form (`sk-ant-oat`/`ort`, a bearer, `eyJ…`,
  `gho_`/`ghu_`, `tid=`) or a handle. The evidence folder holds none either.

The stage was destroyed after the run ([`stage-destroy.txt`](spi-1171/stage-destroy.txt): 11 resources deleted).

## Escalations

1–4 above are the owner's accepted decisions. Others, provisional:

5. **Claude Code on a refused sign-in** fails at session open with t3's generic text (SPI-1172 E1), not one naming the
   sign-in. The relay does answer it naming the sign-in; t3 does not show that answer. Recommendation: leave to the
   follow-up of SPI-1172's E1.
6. **The leak check sends a sign-in's refresh token to the Workspace DO** (by value for its own files, by hash into the
   Container's scanner), through the owner's admin route only. Recommendation: accept: the scan is the proof the ticket
   asks for, and it stays in the Workers.
7. **The token's short id in the relay's log** (32 bits of its SHA-256), for sign-ins only (long random tokens), so a
   renewal can be seen. Recommendation: accept.

# SPI-1169: OpenCode through the model relay

OpenCode threads run on every Model endpoint whose API OpenCode speaks (Anthropic Messages, OpenAI Responses,
OpenAI-compatible Completions) through the model relay (SPI-1167), with the process's model handle as each provider's
key. Decision record: [ADR-0016](../adr/0016-no-vendor-credential-enters-a-container-and-cli-agents-reach-the-model-proxy.md)'s
SPI-1169 refinement; [ADR-0034](../adr/0034-model-endpoints-are-the-owners-set-in-the-harness-panel.md) items 6 and 7;
fragility [U76](../upstream-fragility.md#u76-opencode-on-model-endpoints-through-the-model-relay-spi-1169).

## How OpenCode handles several endpoints

OpenCode takes **a base URL per provider**, and several providers per process. So each endpoint is its own OpenCode
provider, `t3flare-endpoint-<endpointId>` (Codex's prefix, now `endpointProviderId` in `@t3flare/models/relay`, so no
endpoint id takes one of OpenCode's catalog providers such as `openai` or `openrouter` and inherits its entry), at the
relay's **per-endpoint path**. The model-routed URL is not needed and not used: the relay reads no OpenCode body. A
model switch between endpoints, across APIs, stays in the thread's process and its native OpenCode session (p1169).

| API | OpenCode package | Base URL | The wire |
| -- | -- | -- | -- |
| Anthropic Messages | `@opencode/ai/providers/anthropic-compatible` | `…/t3flare/model/<id>/v1` | `/v1/messages`, `x-api-key` |
| OpenAI Responses | `@opencode/ai/providers/openai-compatible-responses` | `…/t3flare/model/<id>` | `/responses`, `authorization: Bearer` |
| OpenAI-compatible Completions | `@opencode/ai/providers/openai-compatible` | `…/t3flare/model/<id>` | `/chat/completions`, `authorization: Bearer` |

An endpoint's base URL follows pi-ai's convention (Anthropic's without `/v1`, OpenAI's with it), so only the Anthropic
package's base URL adds `/v1`. Other APIs' endpoints (Google, Mistral) are not offered to OpenCode. The paths were
measured in `test:docker` and on p1169.

## Where the handle is (the brief's question)

The Workspace DO puts the handle in the process's environment (`T3FLARE_MODEL_HANDLE`), as for Codex and Claude Code.
The launch chain is `setsid --wait /opt/t3flare/bin/opencode acp` (the process command's) → the launcher, which execs
`opencode acp` **without** the handle (`env -u`) → `opencode serve --stdio --port 0`, the server it starts, where
plugins run. So no OpenCode process holds the handle in its environment, nothing OpenCode starts (shells, a
repository's MCP servers and plugins) inherits it, and a repository's `{env:T3FLARE_MODEL_HANDLE}` finds nothing.

The plugin reads the handle from setsid's start environment (`/proc/<pid>/environ`), walking up from the server's
parent, and only from a process whose command line is exactly the launch chain's setsid and whose marker
(`T3FLARE_EXEC`) is this process's (`relay.js` `handleFrom`); otherwise it sets no key and the process's requests get
401. It never puts the handle in OpenCode's settings: the endpoint providers get a placeholder API key (which the
Responses package needs before it will send, and which the relay refuses), and OpenCode's `http.request` hook puts the
handle in the key header (`x-api-key`, or `authorization: Bearer`) only of a request whose URL, as sent after every
setting has applied, is the relay's for that provider's endpoint (`putHandle`). The launcher's watcher and snapshot loop
start without it. No file holds it.

**What this does not do.** It keeps the handle out of environments and files, not out of reach of the Container's
commands. setsid's start environment holds it, readable by any process of the same uid, and everything in the
Container runs as root. A shell OpenCode runs can read it and spend through the handle, for that process's endpoints,
until the process exits. That is the same class as Codex's and Claude Code's, not wider; no command can take an
endpoint's key out of the Container (ADR-0016's residual).

**OpenCode's own APIs** (the reviewer's reading of OpenCode's source, not measured here): `opencode serve --stdio`
binds 127.0.0.1 with a random password, and its remote tunnel exists only in service mode; ACP advertises model ids and
names only; `GET /api/provider/:id` returns a provider's settings unredacted, but only to a client inside the
Container, and a preview of the Container needs a `0.0.0.0` listener. Since review round 1 those settings hold the
placeholder, not the handle. OpenCode also watches `/etc/opencode` and reloads it live: the file is the Container's, so
a newer spawn's configuration reaches running processes. A provider the running plugin did not see at its start gets
no placeholder and no handle (fails closed); a relay↔proxy flip while OpenCode processes run can break them until their
next process (U76).

Proved on p1169: the only process whose environment holds the handle is `setsid --wait /opt/t3flare/bin/opencode acp`;
the 2 OpenCode processes and the launcher's 4 loop processes do not; no file in the process homes, `/etc/opencode`,
`/root`, `/tmp` or the repo holds it; a full-access turn's `env > file` has `T3FLARE_EXEC` and neither the handle nor
the nonce. `test:docker` checks the same with the real image layer, plus a repository MCP server's and a repository
plugin's environment (no handle, no nonce), and a hostile repository configuration (below). The launcher's loops were
also run in `ubuntu:26.04` (uutils coreutils 0.10.0).

## SPI-1045

Gone on the relay. The re-ask problem was the proxy key rotating under a process that asked for it once. On the relay
the plugin asks no key helper: the handle is made for the process and stays valid for its whole life, so there is
nothing to re-ask. Shown on p1169: the agents Worker's log has no `model-key` entry from the run (the key route was
never called, with three OpenCode turns and a shell turn), and every OpenCode request at the relay was 200. The proxy
path keeps its single ask (now once per process even if OpenCode sets the plugin up again); the key helper goes at the
hard cut (SPI-1176), which cancels SPI-1045.

## Models in t3's picker

- **Where they come from.** The OpenCode driver's snapshot lists `opencodeModelsOf`: with an endpoint OpenCode
  speaks that lists a model, those endpoints' models by slug (`<endpointId>/<modelId>`), grouped by endpoint, the first
  marked default; else the proxy's. The list refreshes on every endpoint change (`refreshOnEndpointsChanged`, now
  wired for OpenCode as for Claude Code and Codex). t3 sends the slug; `resolveModelId` maps it to
  `t3flare-endpoint-<id>/<model>`, which is what OpenCode's session offers.
- **The proxy's models.** Following SPI-1168's per-Environment choice (the owner accepted it for Claude Code; applied
  here as instructed): with such an endpoint, every OpenCode process runs on the endpoints only, and the Model proxy's
  provider is not configured. Unlike Claude's, t3's registry does not keep the proxy's rows: it keeps an `opencode`
  snapshot's missing models only while its probe is pending or failed (`ProviderRegistry.ts`), and ours is ready. p1169
  listed exactly the 3 endpoint models.
- **Stale ids.** A thread on an earlier proxy model (`anthropic/<id>` → `t3flare/<id>`), or on an endpoint that is
  gone or speaks another API, names a model OpenCode's session does not offer; t3's ACP adapter refuses it before any
  request ("The agent did not accept the model"), as for Claude Code. It is not mapped to another model until SPI-1176's
  fallback.
- **Small model** (`small_model`, OpenCode's titles and summaries): the text-generation model when it is one of these
  endpoints' models, else their small model, else the first model (`relayTextModel`, Claude's background-model rule).
  p1169 set the text-generation model to `resp/claude-haiku-5-5` and OpenCode's `small_model` followed it.

## Escalations (provisional, as assumed)

1. **The relay-or-proxy choice is the Environment's for OpenCode too**, as the brief directs from SPI-1168's accepted
   choice: with any endpoint OpenCode speaks that lists a model, every OpenCode process is on the endpoints and the
   proxy's models are refused in OpenCode threads (ADR-0034 item 6 records it beside Claude Code's). OpenCode's system
   configuration (`/etc/opencode/opencode.json`) is Container-wide, as Claude's managed settings are. Recommendation:
   accept (the owner adds Commissary as an endpoint, as the stage does).
2. **A repository can still send an endpoint provider's requests elsewhere, without the handle.** A model or variant
   it adds to an endpoint's provider is not pinned (OpenCode applies the configuration after every plugin, and the
   system file cannot remove a repository's entry), so a project agent or the `effort` option can send that model's
   prompts to the repository's URL, with the placeholder key. That is what a repository's own MCP server or plugin can
   already do, which stock t3 honours. Recommendation: accept; the handle is what the relay guards.
3. **The plugin names the providers from the process's own copy of its configuration** (OpenCode adds the configured
   providers after a plugin's transform runs), and trusts it only for providers at the relay's URL; the handle goes
   only into requests to that URL. Recommendation: accept (U76 has the file's permissions).
4. **The key header is set at request time** (`http.request` hook) rather than as a setting. If OpenCode drops the
   hook, OpenCode fails closed (401). Recommendation: accept.
5. **Models with `reasoning` get t3's effort picker** (as on the proxy), but OpenCode's provider entries declare no
   reasoning capability, as the proxy's did not. Effort may be ignored by OpenCode for these models. Recommendation: a
   follow-up if the owner wants effort on endpoint models (OpenCode's `capabilities.reasoning`).
6. **OpenCode's failure texts still name the Model proxy's key** (`cliPromptFailure`) on a 401 from an endpoint. Left
   for SPI-1171, as SPI-1168 left Claude's.
7. **An endpoint added while an OpenCode process runs** is in its handle's scope and configuration only from its next
   process (403 until then), as for Codex and Claude Code.

   (provider, model, variant) applied, is the relay's for that provider's endpoint (`http.request` hook, `putHandle`).

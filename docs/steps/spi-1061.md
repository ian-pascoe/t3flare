### Standards

Sources: `AGENTS.md`, ADR-0001 (Layer, then Shadow, then Patch), ADR-0030, `docs/upstream-fragility.md`, the repo's lint and Effect diagnostics, and the smell baseline.

- **Fixed:** I found three code smells and fixed all three before the final check.
  - Duplicated Code: `findSession` was in both `outbound.ts` and `peerAcceptance.ts`. It is now exported from `peerAcceptance.ts`.
  - Duplicated Code: `tailing` was copied from `tools.ts`. Both now use `lib/tail.ts`.
  - `Standin.logs()` ran `docker logs` twice.
- **Judgement calls, kept:**
  - `outbound.ts` is long, at about 500 lines across seven phases. That is the pattern of `tools.ts` and `peer-e2e.ts`.
  - `alchemy.run.ts` casts `standinCredentials as never`. This follows the file's existing `as never` uses on alchemy's types.
- **Hard violations:** none.
  - The Layer over t3's service follows ADR-0001.
  - The submodule is untouched.
  - No pnpm command ran inside `t3code/`.
  - `lib/tail.ts` and `lib/standin.ts` read the alchemy profile and the 0600 stand-in file by script only, as `tools.ts` and `stage.ts` already do, and print neither. I opened no credential file.

### Spec

- **Implemented as asked:**
  - M1 in full, including the kept `cause` stripping. Before, the Layer replaced `link`, `list` and `resolve` and stripped `cause` only on `get` and `unlink`; it now strips `cause` on all five methods.
  - M2: D7's hold, 5/15/30 backoff, DO-storage state, alarm merge, standing alarm and deploy survival.
  - M3's leak canary and C6.
  - Every gate and check except the parts listed next.
- **Partial:**
  - G4's T3 Connect publish is SPI-1094.
  - C6 on the call path is an HTTP 502, not a transport error (above).
  - C7's expiry is not staged.
  - G5, the prod link and the same-zone path (D23) are the owner's.
- **Different from the plan, and why:**
  - The standing alarm is kept only once the idle check reads t3's tables, which happens after the idle delay with no client. While a client is connected there is no standing alarm. A deploy then gets a reconnect, which boots t3 and resumes the followers. This is how ADR-0003 already treats an Environment with a client.
  - Stale retry state outlives a task's end until the next reset. It wakes nothing (`remoteWakeAt` returns null with no open task), and `planReset` deletes it.
- **Scope beyond the plan:**
  - `remoteRetry` on the health route, for C4's evidence.
  - The fault relay in the stand-in image, for C6.

Total: Standards 3 findings, all fixed. Spec: 4 partials, all recorded, and 2 deliberate differences. The worst within Spec is C6's call path, which is proved as an HTTP failure rather than a transport error.

## For the owner

Run this when you are back, against your real desktop app, on a **fresh** stage that is destroyed at the end (it will hold a real bearer for your laptop). Use a scratch project on the laptop. Tick each step with a screenshot. Part one takes about **25 minutes** attended. Part two takes about **35 minutes** more, mostly one-time setup, and can be a second sitting. The prod check at the end takes about **10 minutes**.

**Setup (agent-side, before you sit down).** Deploy a fresh stage without the stand-in: `node scripts/stage.ts deploy <stage>` (no `T3FLARE_STANDIN`). Pair your desktop app to it.

**Part one, over T3 Connect (about 25 minutes).**
1. **Link.** In the desktop app, open Linked environments on the stage Environment → Link → your laptop, at the access you want. The laptop's Sharing & access should show the stage's session at that access.
2. **A round trip.** Ask the stage's Durable agent to delegate a small task to the laptop. The thread should appear in the desktop app marked "From" the stage's name. When it ends, the cloud task completes and its parent wakes with the reply.
3. **The agent asks.** Unlink. Ask the agent to link the laptop. t3's link card should appear in its thread; pick the machine and the access, and the agent should go on.
4. **Sleep.** Start a longer task, then close the lid or cut the laptop's network for ten minutes. Do not quit the app, which would end the running turn. On reopening, the task should complete. The stage's `/_t3flare/health` shows `remoteRetry` while it waits.
5. **Ending it.** Unlink in the client, then revoke the stage's session on the laptop. An open task should fail with t3's reason.

**Part two, the other Routes (about 35 minutes).** Follow `docs/outbound-link.md`.

6. **Tailscale Funnel (about 20 minutes, up to 10 of them waiting for DNS).** Pin t3's port, run `tailscale funnel --bg <port>`, and check the descriptor at the public `.ts.net` address. Link by typing the address and pasting a pairing code from the laptop. Then do one round trip.
7. **Your own Cloudflare Tunnel (about 15 minutes).** Set up a tunnel and a hostname to `http://localhost:<port>`, with no Access, and run `cloudflared` as a launch agent. Link by address, then do one round trip.
8. **Teardown.** For each of the two, either keep it for prod's own link or turn it off: `tailscale funnel … off`; delete the launch agent, the tunnel and its DNS record. Then unlink, revoke on the laptop, and destroy the stage.

**Then, on prod (about 10 minutes).** Link prod over the Routes you chose and do one round trip. If your tunnel's hostname is in `ianpascoe.dev`, do one round trip over that Route alone: prod is the only place the same-zone path exists (D23, U47). If it fails, move the hostname to another zone, or that Route waits for SPI-1072.

# SPI-1163: Text generation on any Model endpoint's model

Thread titles, commit messages and PR text now run on any Model endpoint's model, not only through the Model proxy.
The text is one pi-ai request on the agents Worker, called from the Environment DO, so the Environment's bundle never
holds pi-ai. The text-generation setting can name any `<endpointId>/<modelId>`. While the owner has picked no model,
the setting names the default: a small model of the first endpoint that has one. ADR-0034 §5 records the design.

### How the key reaches the request (the brief's question)

**No key and no endpoint cross the Environment→agents call.** The call carries the endpoint's id, the model id and the
prompt (review round 1: ids only). The agents Worker reads the endpoint with `modelEndpoints()` and asks for its key
with `endpointCredential({ endpointId, target })`, both on the Environment DO, exactly as a Session does (ADR-0018). The
key comes back in that answer, which is the existing Session pattern.

I chose this because it reuses the target rule unchanged: the Environment gives the key only for the endpoint's current
target, and no caller-supplied endpoint shape exists on the agents side. Passing the key in the call would have been a
second path that the target rule does not guard.

### The subscription seam

Text generation builds its request with `endpointProviders`, the same provider code a Session uses, so a sign-in's
credential reaches both through one place. It is not free, though. SPI-1164 still has to touch, for text generation as
for Sessions:

- `endpointProviders`' resolver, to take a sign-in's access token from the broker;
- `ENDPOINT_STREAMS`, for a sign-in's own APIs (such as Codex's backend);
- the texts that say "API key": `credentialProblem`, and `statusProblem`'s 401/403 text for a keyed endpoint.

Nothing in `endpointTextGeneration.ts` or `runText` checks the API, so neither needs a change. The list is in the
comment at the top of `endpointTextGeneration.ts`.

### Errors

Each failure names the endpoint. The text comes from our own fixed strings, never from the vendor's body:

- **401/403:** "refused its API key (HTTP n): check it in the Harness panel"; for an endpoint with no auth, "refused
  the request without a credential (HTTP n): check its auth in the Harness panel".
- **404:** "does not serve the model m".
- **429:** "is rate- or usage-limited".
- **Other 4xx:** "refused the request".
- **5xx:** "failed (HTTP n)".
- **No answer:** "could not be reached".
- **Timeout:** "did not answer in time" (110 s on the agents Worker, inside the Environment's 120 s).
- **A reply that is not the JSON asked for:** "The Model endpoint "e" (model m) returned invalid structured output."
- **A malformed request:** "The text generation request was malformed: …".
- **No key:** the same reasons a Session's turn gives (no key, unreadable, changed).

On the Environment side:

- The endpoint was removed: "was removed: pick another model for text generation".
- The endpoint no longer lists the model: "no longer lists the model m".
- An agents-Worker transport error: "could not be used for text generation: the agents Worker could not be reached".
  The platform's error text is kept only as the cause.
- A failure t3's own operations add, after the reply (a placeholder title, `generatedThreadTitle`) or before the request
  (no investigation, `withoutInvestigation`), is prefixed `The Model endpoint "e" (model m): …` by
  `makePiDurableTextGeneration`'s wrapper. That covers every operation: t3's other post-decode steps (the commit, PR and
  branch sanitizers) do not fail.

The status is read through the request's `fetch` for Anthropic Messages and the two OpenAI APIs, and through pi-ai's
`onResponse` for Mistral (its adapter calls it before it throws on an error). Google's adapter refuses a custom fetch
and calls no `onResponse`, and pi-ai's error message is never used here (it can carry the body), so a Google endpoint's
HTTP failures all read "failed (its API reports no status here)". That stays until pi-ai exposes the status.

`proxyFailure.ts` was not reused: its table is Commissary's own contract (cooldowns, spend limits). The generic status
mapping fits any endpoint.

    body and the key are absent from every message.
  - **Other failures:**
    - unreachable;

    - an empty answer.
- **`runText`** (`apps/environment/test/endpointTextGeneration.test.ts`):
  - **Endpoint path:** the call carries ids only, and no key (the proxy key is not in it either); the agents Worker's
    error is passed on; a transport failure names the endpoint, not the platform's text; a reply that is not JSON
    names the endpoint and its model.
  - **Default and proxy:** `default` resolves to the first endpoint's small model; `anthropic/…` still goes to the
    proxy.
  - **Failures with nothing called:** a removed endpoint or model, and no binding.
  - **Nothing usable:** no small model and no proxy gives guidance.
- **The setting's default** (`apps/environment/test/textGenerationDefault.test.ts`, on t3's test settings service):
  - **Replaced:**
    - t3's own default, with Codex registered or not;
    - the old seed (`anthropic/claude-haiku-5-5`), which then follows endpoint changes.
  - **Fallbacks:** the proxy's small model when no endpoint has one; `default` with no proxy and no small model.
  - **Kept:** a model the owner picked, including after the default had been written.
  - **Each "unset" clause on its own:** an unregistered instance that is not t3's default; `default` while the record
    names another model.
  - **The record and the order:** a failed write records nothing; two endpoint changes, the first write the slower,

    setting.
- **The entrypoint** (`apps/agents/test/endpointTextGeneration.workerd.test.ts`, in workerd): a malformed request,
  including one carrying an endpoint object, is refused before the Environment is asked anything; a valid one reads the
  endpoint from the Environment, and an id it no longer has fails naming it.

## Escalations (assumed provisionally)

1. **What "no model set" means for the setting.** t3's setting always has a value, so "unset" is one of:
   - t3's own default, `codex`/`gpt-6-luna`;
   - an unregistered instance;
   - `default`;
   - the model this sync last wrote (stored in the DO);
   - the earlier seed, `anthropic/claude-haiku-5-5`, before any record exists.

   Three consequences:
   - **Some picks are never kept.** A pick equal to t3's `codex`/`gpt-6-luna`, or to the default the sync last wrote, is
     read as unset: it is replaced at every boot and every endpoint change, not once. To keep the current default
     fixed, the owner picks another model. Upstream-fragility U67 records it.
   - **An earlier explicit pick may be replaced once.** An owner who deliberately picked the proxy's
     `claude-haiku-5-5` before this change sees it replaced by an endpoint's default. The hard cut moves `anthropic/…`
     selections to the default anyway.
   - **Text generation leaves Codex.** On `main` the setting stayed at Codex's model on every Cloud Environment: step
     4a registers a `codex` instance, so the old "unregistered instance" seed never ran (the first p1163 run showed
     this). Text generation therefore ran through the Codex CLI. It now moves to Pi Durable's default. The ticket asks
     for this, but it changes prod's behaviour at the next deploy.

   Recommendation: keep all three as built.
2. **The small-model rule:** a word-match on the id (haiku/mini/nano/flash/lite/small/tiny), then the cheapest known
   output price. Recommendation: keep it. The owner can always pick a model, and the setting shows which one is in use.
3. **The default when no endpoint has a small model:** the proxy's small model until SPI-1176. SPI-1176 should drop
   that branch in `textModelOf` and `syncTextGenerationDefault`; after it, the setting reads `default`, which fails
   saying to pick a model.
4. **Reasoning:** text generation sends no reasoning level, so each model uses its own default, with
   `maxTokens = min(model, 8192)`. Recommendation: keep it; revisit if a reasoning model spends the budget thinking.

## Review round 2

1. **Every endpoint-path failure names the endpoint and model.** `makePiDurableTextGeneration` wraps each of t3's six
   operations. A failure on an endpoint's model that does not name it yet becomes `The Model endpoint "e" (model m):
   <detail>`. This covers `generatedThreadTitle`'s placeholder title and `withoutInvestigation`'s refusal; t3's other
   post-decode steps cannot fail. Tests cover the placeholder title (explicit slug and `default`), the review guide's
   refusal, and both unwrapped cases (a failure already naming the endpoint, and the proxy's). The comments in
   `textGeneration.ts` and the test header say this.
2. **U67's fixes:**
   - Detection cites `apps/environment/scripts/p1163.ts`.
   - Its first "Breaks when" is t3 no longer deriving its default from `DEFAULT_SERVER_SETTINGS`, which the sync reads
     live.
   - It now records the timeout and the scope.
3. **A hung sync can't block later boots.**
   - Listener syncs are forked into the layer's scope (`Effect.forkIn`), so the runtime's disposal interrupts them.
   - Every sync is bounded by `SYNC_TIMEOUT_MS` (30 s) inside the permit.
   - Test: a sync hung on a settings read is interrupted when the scope closes, and a later sync runs. It fails with
     the old root fiber.
4. **A landed write is recorded, with one known gap.** The record is the write's exit handler (`Effect.onExit`). A
   failed or interrupted write records nothing. I didn't make the write itself uninterruptible: a hung write would
   then hold the permit past the timeout (item 3). Round 3's spec review showed the gap this leaves. t3's
   `updateSettings` writes inside `Effect.uninterruptibleMask`, so a write slower than `SYNC_TIMEOUT_MS`, or a
   disposal mid-write, can land while the exit reads as interrupted. That default then goes unrecorded and stops
   following the endpoints. This is accepted: it needs a write slower than 30 s, and the comment in `seedSettings.ts`
   says so. The interleaving has no deterministic test.
5. **A Google endpoint's failure** reads `The Model endpoint "e" failed (its API reports no status here).` (test).
6. **`docs/model-proxy.md`:** the classification line and the "not configured" line now say they apply to the
   proxy's models (`anthropic/…`).
7. **Checks:** recorded below. Escalation 1 now ends "keep all three as built".
8. **Nits:**
   - `MAX_TEXT_TOKENS` is no longer exported, and the redundant assertion is gone.
   - `endpointLabel(id)` in `@t3flare/models/endpoints` is used by both Workers and by `credentialProblem`.
   - `late` is renamed `timedOut`.
   - The `void context;` is gone.

The p1163 evidence was re-run, because the setting's endpoint-change sync changed (it now forks into the layer's scope).
Every check passed, including the setting following the saved endpoints; the stage is destroyed.

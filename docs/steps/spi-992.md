## What was built

- **No write token in any Container (OD-2).** The Container token is `contents: read`, `pull_requests: write`,
  `metadata: read` (`packages/github-app/src/permissions.ts`, review M4). The credential helper (`v=2`) answers only
  `https` + `github.com` and the Workspace DO's endpoint issues only read tokens (item 10: an old repo helper gets
  nothing; the router no longer passes `T3FLARE_GIT_TOKEN`).
- **The push gateway** (`apps/agents/src/workspace/pushGateway.ts`, the `WorkspaceProxy` route
  `computer.internal/t3flare/git/…`). The image's system gitconfig (`apps/sandbox-image/image/gitconfig`, OD-1, review
  M5) rewrites every push to github.com there; nothing is written per Container start. The gateway is strict (review
  M1): exact `?service=git-receive-pack`, strict pkt-line grammar (hex lengths, 40/64-hex oids, `check-ref-format`
  names, 64 KiB prefix cap, ≤ 64 updates), any `Content-Encoding` refused, a probe answered with a constant `0000`,
  the command list re-serialised from the parsed updates with an allowlist of capabilities, upstream headers from an
  allowlist. It asks the Workspace DO (`authorizePush`) and forwards an allowed push with a **gateway token**
  (`contents: write`, + `workflows` when opted in) that never enters a Container or a Session.
- **The policy** (`linkedPush.ts` `pushDecision`): allow on an **expectation** (t3's own push argv, review M2:
  `push -- <remote> HEAD:refs/heads/<b>`, bare `push` through `@{push}`, the stack rebase's `--force-with-lease` form,
  `--delete`; bound to the Workspace and `{ref, new}`, registered before the router's git command and removed after,
  30-minute cap) or an untainted Workspace; **ask** while tainted (on the linked thread when live, else the one owner
  thread pushing: a Durable Session with a command running or one owner CLI process in a turn); else **refuse** with a
  named message.
- **Durable taint (review H1).** `t3flare:taint` on the Workspace DO, set by linked work (Durable commands and linked
  CLI processes), survives the 30-minute window, Container stops and DO restarts; worktree Workspaces inherit it. The
  owner clears it with `POST /_t3flare/agents/workspace-trust` (admin) or the owner card's labelled trust answer.
- **The card (review M6, M7).** GitHub's advertised tips against the update (create, delete, force-push, tag, default
  branch), the Workspace's claims (subject, fast-forward) labelled as such, non-ASCII escaped. Its own buttons
  (`pushCardOptions`): a linked card offers "Allow this push" and "Decline" only; an owner card in a tainted Workspace
  offers "Allow this push once" and, in t3's "more" menu with a warning, **"Allow and trust this Workspace again
  (clears the linked-work mark)"** — the only answer that clears the taint (never t3's default "Always allow this
  session" wording). A card whose git went away is withdrawn; a pending ask counts as open work for the idle reset.
- **SPI-1040: CLI threads.** The Environment DO's `approvePush` → `provider/cli/linkedPushAsk.ts` (thread → asker
  registry) → the CLI wrapper (`provider/cli/wrapper.ts`), which raises t3's "Allow git push?" card on the thread's
  live turn (injected `runtime_request.updated`, `node.updated`, `turn_item.updated`), answers t3's
  `respondToRuntimeRequest` for its own id prefix, withdraws the card when git goes away, and closes it before t3 sees
  the turn end. The CLI never sees the card. The step-4a `cli:` refusal is gone. The ACP driver's adapter options
  (`acpAdapterOptions`) pin "no `clientTerminals`" (review M3).
- **Router** (`processRouter.ts`, `gitRoutes.ts`): push → expectation, no token; the gateway URL mapped back to
  `https://github.com/` in `remote -v`/`get-url`/`config --get remote.*.pushurl` output for t3.
- **Admin and probes** (test stages only, `T3FLARE_FAULTS`): `workspace-taint`, `workspace-trust`, `probePush`
  (hold, lapse, note linked work).

## Findings worth keeping

- **Codex at auto-accept-edits cannot push at all**: Codex runs commands in its own sandbox without network, so `git push` exits 128 before it reaches the gateway (no card, nothing pushed). A linked Codex thread pushes only through a full-access link (where it is asked as any other). Fail-closed; recorded here and in SPI-1063.
- **Ask order picks a lingering linked thread first**: while a linked thread's work counts as live (its window, or its CLI process alive), a push in that Workspace is asked on that linked thread, even when the owner's thread ran it, because the gateway sees refs, not the caller. If that thread has no live turn the push is refused ("no live turn to ask on"). Fail-closed and per H1's order; the owner can push with Commit & push (an expectation) or trust the Workspace. Seen on stage when a previous run's OpenCode process outlived its turn.
- **A Workspace runs few CLI processes** (Claude Code and OpenCode count twice): a second CLI thread in the same Workspace is refused while earlier ones live (seen as "Provider session failed to open"). Pre-existing (step 4a); the harness stops the Container between CLIs.
- **The card's buttons are t3's own feature**: `approval_request.options` (`ProviderApprovalOption {decision, label, warning}`) replace t3's default buttons; decisions other than `accept`/`decline` go under "more". This is how the owner card avoids "Always allow this session" for the trust answer.
- **A full-access link is trusted like the owner** (t3's documented exception, the Link fence): it can answer cards. F7 (an auto-accept-edits link cannot answer) holds (`m2-hostile-durable.json`).
- **Large files and the Workspace DO**: P3's 90/110 MiB fixtures made the Workspace DO run out of memory syncing them (SPI-1050).
- **One unexplained owner push failure** in an early persist run (t3's push failed without reaching the gateway) did not reproduce in 6 tries (SPI-1051).
- **The model proxy's usage limit** ended one Codex turn while its card waited; the wrapper closed the card ("the turn ended") and nothing landed: the turn-end path, on stage.

## Code review (vs `origin/main` 66e0350, two axes)

Done by the implementer, one axis after the other (the `code-review` skill's subagents were not available to this agent); the security axis read the gateway route, `pushGateway.ts`, `linkedPush.ts`, the Workspace DO's credential, policy and probe paths, the router and the CLI wrapper.

**Correctness and security.**
- No token that writes code leaves the agents Worker: the gateway token is minted per request by `pushTarget`, used only in the upstream `Authorization`, never echoed (GitHub's response is streamed back; our headers are allowlisted both ways), and hashed into the leak scan (`gateway-token`), which found nothing on stage.
- The policy's callers are as stated in ADR-0013: `authorizePush` only from `WorkspaceProxy`'s gateway path, `expectPush`/`unexpectPush` only from the Environment's router over DO RPC; `probePush`/`probeProcess` refuse outside `T3FLARE_FAULTS` stages.
- The wrapper's push cards cannot be answered by the CLI (they never reach it) and cannot collide with a CLI's own requests (their id prefix needs a provider turn id of `t3flare-push`). Fixed during review: t3's `acceptAlways` now approves once (it trusted before); the abort listener is removed when a card is answered (it lingered up to the 10-minute timeout); a lint finding (useless spread).
- `linkedPushAsk.ts` keeps a module-level registry (thread → asker): sound because one Environment DO serves the deployment (`ENVIRONMENT_NAME`) and thread ids are unique; noted for a future multi-Environment Worker.
- Residuals, all documented: a full-access link can answer cards (t3's exception); a hostile Container can still read with the read token; the expectation race; the lingering-linked-thread attribution (fail-closed).

**Design and maintainability.**
- The card is one function (`pushCard`, with `pushCardOptions`) used by both the Durable and the CLI paths; the policy is one pure function (`pushDecision`) with a table test; the gateway is one module with real-git tests against a local stand-in.
- The CLI wrapper grew (turn tracking, injection, interception) but stays one seam around t3's adapters, shared by all four CLIs; its reliance on t3 internals is U37 with a scripted-agent test.
- `scripts/spi992.ts` is a stage harness, not acceptance (SPI-1062 folds it in).
- No blocking findings remain.

## The symptom, reproduced

The harness (`p1100.ts`) follows the web client. It opens a worktree thread for each agent, and the agent writes
`notes.txt` as `one` in turn 1 and as `two` in turn 2. It reads t3's turn diffs (`orchestration.getTurnDiff`) 0→1 and
1→2, then rolls back to turn 1 with files restored (`checkpoint.rollback`, "Revert to this message"). Stage `p1100` ran
`main`'s code:

| Agent | `notes.txt` (`projects.readFile`) | Diff 0→1 | Diff 1→2 | Evidence |
| --- | --- | --- | --- | --- |
| Codex | `one`, `two` | `+one` | **empty** | [`before-codex.json`](spi-1100/before-codex.json) |
| Claude | `one`, `two` | **empty** | **`+one`** (new file) | [`before-claude.json`](spi-1100/before-claude.json) |

Claude's checkpoints run one turn late: checkpoint 1 is missing `notes.txt`, and checkpoint 2 holds turn 1's `one`.
That explains SPI-997's Claude rollback, where restoring checkpoint 1 deleted `notes.txt`. Codex's turn 1 happened to be
captured in time, but its turn 2 was not. Every capture in the checkpoint trace ran `by: "do"`, on the Workspace DO's
files.

## Root cause

A turn's checkpoint is taken from the Workspace DO's copy of the files before the Container's writes reach it.

- t3 captures a turn's checkpoint as soon as the turn ends (`CheckpointService.capture` → the driver's
  `captureCheckpoint` → `WorkspaceDO.checkpoint`). Within the guard, `#capture` commits the DO's own files with
  isomorphic-git. Above the guard, it aliases the last capture when the DO's change log has nothing new since.
- A CLI agent writes in the Container. Its writes reach the DO only when `TerminalSync` pulls them. That pull is
  debounced on the process's output: it waits 1 s after the output goes quiet, and the wait doubles up to 60 s while
  pulls find nothing. The turn's own last output (its completion) restarts that wait, so the pull always comes after
  the capture.
- The Durable agent writes through the DO, so its captures were always right. The checkpoint diff itself is correct,
  because it compares two commits. Only the commits were wrong.

Hypotheses, ranked before the fix:

1. Capture before pull (the ticket's suspect). Prediction: the turn's write is in a later checkpoint, and pulling
   before the capture fixes it. **Confirmed**: Claude's checkpoints lag one turn, and the fix turns all five agents
   green.
2. Capture against the wrong backend (DO rather than Container). This is the same mechanism seen from the other side:
   the DO path is correct once the DO is current, so no Container capture is needed within the guard.
3. Above the guard, an alias over an empty journal. That path is not taken for the fixture (within the guard), but it
   has the same cause, and the regression test covers it.
4. The pull never brings the file. Ruled out: the DO's `readFile` shows each turn's content shortly after the turn.

## The fix

- **`apps/agents/src/workspace/checkpointCapture.ts`** (new): `captureTurn` is the capture decision taken out of
  `WorkspaceDO.#capture`, with one change. It first pulls the Container's writes. Only then does it read the change
  log's revision, HEAD and the files, and choose between a DO commit, an alias and the Container's git. If the pull
  fails, the capture fails and writes no ref: a checkpoint without the Container's writes would be wrong, not just late.
- **`WorkspaceDO.#capture`** calls it, with `pull` = `TerminalSync.pullNow()`. That pull is serialised with the
  terminals' own pulls and runs the sync guard's scan (review F3). It never starts a stopped Container, and a stopped
  Container has nothing left to pull, because a stop pulls before it ends.
- Cost: a capture takes about 200–400 ms instead of 50–160 ms (the trace in `after.json` against `before-*.json`). t3
  makes at most two captures per turn.

### ACP rollback on (SPI-1037)

With correct checkpoints, Claude and OpenCode rollback was tried again, and it now works:

- `acpDriver.ts` `acpCapabilities` keeps t3's ACP rollback capabilities (`canRollbackThread`,
  `providerCanRollbackConversation`) and no longer turns them off.
- `wrapper.ts` runs the adapter's `rollbackThread` under `CliSpawn`. t3's ACP rollback starts a replacement agent
  process (`startReplacementAcpRuntime`), which is now spawned as the session's, with its thread and tool handle, as
  SPI-997 asked. After OpenCode's rollback, its worktree held exactly one process, marked with the thread. This step was
  not isolated: the rollback was not also tried without it.
- The conversation result is stock t3's: ACP has no truncation, so the agent starts a fresh session and keeps none of
  the conversation, the kept turns included. After the rollback, Claude and OpenCode answer `NONE`.
  SPI-997's Claude still listed all three code words, and that is not seen here.

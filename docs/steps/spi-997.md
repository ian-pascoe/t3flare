## Which path

**Native fork, not the handoff.** pi-durable forks a conversation inside one Session, but each t3 thread has its own
Session DO, so a fork across threads cannot be a pi-durable fork. Instead the new thread's Session is seeded from the
source Session's model context. t3 resolves the fork as `native_fork`. If the native fork fails, t3 still falls back to
its portable context handoff (`ProviderTurnStartService`), which the policy test below also covers for a busy source.

**Rollback is a pi-durable fork.** Entries are immutable, so nothing is rewound in place. Like t3's Pi adapter, which
forks its session file at an entry and switches to it, the Session forks its conversation and runs the fork.

## What was built

### The Session's conversation (`apps/agents/src/session/SessionDO.ts`)

- The Session no longer assumes the Harness's root. A pointer in its storage (`t3flare:conversation`) names the
  conversation it runs; with no pointer, it runs the root, as before. Every command, push, snapshot, watch and Todo read
  goes through `#conversation()`.
- `#moveTo` sets the pointer and ends the watch on the old conversation, so the next push reads the new one.
  - Entry ids are session-wide and only grow, so the push cursor needs no reset.
  - A fork's `entries()` include the inherited entries, so a snapshot still attributes the kept turns.

### Rollback (SPI-987)

- **Adapter** (`rollbackThread`): refused while a turn runs. It sends the Session the provider turns after the target's
  ordinal (all of them for `thread_start`), and answers with the provider thread as the snapshot, as t3's Pi adapter
  does. t3 then restores the files through our checkpoint route (`WorkspaceDO.#restore`, the Container's git), marks
  the later runs `rolled_back`, and writes the thread back.
- **Session** (`rollback`):
  - It is refused while a turn is live.
  - `rollbackPlan` drops the named turns, plus any turn placed at or after the first of them.
  - `rewind` forks the conversation at the entry before that turn's input. With no entry before it (rolling back to
    the thread's start), it opens a fresh conversation with the same model, thinking level and cwd.
  - The old conversation is aborted and kept as history. The dropped turns, their model-proxy records, and any
    approval or question left over are forgotten.
  - A repeated call finds nothing to drop and changes nothing.
- **Code mode.** A script's journal is a task document (`pi.codemode.journal`) and retires with its task; no task is
  live at a rollback. Code mode's `store` is `fork: "asOf"`, so the fork sees the values as they were at the fork
  entry. A unit test shows a value written in a dropped turn is gone.
- **Not rolled back** (SPI-1101): the Todo List and context Notes are `fork: "current"` and keep their latest values.
  Changing that changes their stored shape.

### Fork (SPI-997)

- **Adapter** (`forkThread`):
  - It runs in the target thread's session, where t3 calls it.
  - It checks that the source is another Durable session (`nativeThreadRef`, `thread:<id>`).
  - It registers the new provider thread with `forkedFrom` (the source thread and turn), then asks the Session to fork
    from the source Session.
- **Session** (`fork` and `forkSource`):
  - The target opens a fresh conversation and asks the source Session directly, over the agents Worker's own
    `SESSIONS` binding.
  - `forkSource` finds the fork point (`forkPoint`): the last entry before the next turn's input, or the newest entry.
    It returns the model context as of there (`Conversation.context({ at })`, compaction included), in pages of up to
    4 MiB under DO RPC's 32 MiB.
  - The target writes the pages as `t3flare.fork` entries of up to 512 KiB, under the 2 MB row limit, and switches to
    the new conversation.
  - These entries belong to no turn, so the differ never shows them; t3 shows the fork's history from its own
    transcript.
  - The fork is recorded (`t3flare:fork`): a repeat of the same fork is answered, not seeded twice. A different fork,
    or a fork into a Session that has turns, is refused.
- **Not carried over** (SPI-1101): the source's documents (code mode's `store`, the Todo List, Notes, loaded tools).
  A pi-durable fork would keep them, but these are two Durable Objects.

### Capabilities

`canRollbackThread`, `canForkThread`, `canForkFromTurn`, `providerCanRollbackConversation` and
`providerRollbackReturnsSnapshot` are now true. The web client's "Revert to this message" was always offered, since
Pi Durable never set `supportsConversationRollback: false`; it now works.

its replacement agent process there, and that process must become the session's, with its tool handle.
